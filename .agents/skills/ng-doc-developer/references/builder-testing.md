# Testing the builder

The legacy builder code is tested with Vitest through `npx nx test builder` (`libs/builder/vitest.config.ts`, one file at a time). The legacy-engine children of `testing/modernization/legacy-generator.spec.ts` must stay serial even though each has its own fixture root: the legacy engine compiles every entry module to `engine/.cache/<path relative to the docs>.mjs` next to the built engine (`CACHE_PATH`), so two builds of fixtures with the same layout overwrite and remove each other's modules. The generator engine (`libs/builder/generator`) has its own suites and a dedicated runner with per-group coverage gates. Nx does not run the generator's Vitest suites; use the runner or Vitest directly.

## Test file conventions

| Kind                       | Name                               | Runner                                   | Where                                                                             |
| -------------------------- | ---------------------------------- | ---------------------------------------- | --------------------------------------------------------------------------------- |
| Generator unit/integration | `*.vitest.ts`                      | Vitest 4                                 | Next to the module (`compiler/`, `outputs/`) or in `<area>/testing/`.             |
| Generator spec suites      | `*.spec.ts`                        | Vitest (`libs/builder/vitest.config.ts`) | `artifacts/testing`, `discovery/testing`, `session/testing`, `generator/testing`. |
| Real-process integration   | `*.integration.ts`                 | Vitest                                   | See "Tests outside the runner groups" below.                                      |
| End-to-end                 | `acceptance/<name>/run.mjs`        | Node                                     | Real filesystem, Angular/Vite, browser, packed tarballs.                          |
| Legacy builder, libraries  | `*.spec.ts`                        | Vitest through Nx                        | Next to the source.                                                               |
| Tool scripts               | `tools/scripts/testing/*.test.mjs` | `node --test`                            |                                                                                   |

The runner's spec groups (`contracts`, `session`, `discovery`, `artifact-cache-commit`) run `libs/builder/vitest.config.ts` limited to their `tests` globs, with the gate over their `collect` files. Spies on `node:fs/promises` need `vi.mock('node:fs/promises', ...)` with a spread copy of the module (see `artifacts/testing/delta-commit.spec.ts`): the namespace of a Node built-in cannot be spied on.

Each generator area has its own `vitest.config.ts`, which declares the `include` globs, coverage `include` (the production files the gate measures) and thresholds. Some configs alias `@ng-doc/core` and `@ng-doc/utils` to their sources. A new test file must match the area's `include` glob, or it will not run.

## The runner: `tools/scripts/check-builder-modernization.mjs`

```sh
node tools/scripts/check-builder-modernization.mjs --list                  # groups: id, lane, runner, timeout, weight, shards
node tools/scripts/check-builder-modernization.mjs --source-check          # layering check only
node tools/scripts/check-builder-modernization.mjs --lane core  --log-dir tmp/runs/<new-dir>
node tools/scripts/check-builder-modernization.mjs --lane posix --group compiler --group worker --log-dir tmp/runs/<new-dir>
node tools/scripts/check-builder-modernization.mjs --weight light --log-dir tmp/runs/<new-dir>   # the light core groups, in parallel
node tools/scripts/check-builder-modernization.mjs --group compiler --shard 2/4 --log-dir tmp/runs/<new-dir>
node tools/scripts/check-builder-modernization.mjs --group compiler --merge-coverage <blob-dir> --log-dir tmp/runs/<new-dir>
```

| Group                                               | Lane  | Runner | Covers                                                                                                                                                                   |
| --------------------------------------------------- | ----- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `source-boundaries`                                 | core  | source | No private Angular CLI imports; `progress/` and `kernel/` layering (below).                                                                                              |
| `contracts`                                         | core  | vitest | `generator/testing/contracts.spec.ts`, `content-module-ids.spec.ts` (builder config, no gate).                                                                           |
| `session`                                           | core  | vitest | `session/testing/**/*.spec.ts`, coverage over `session/*.ts`.                                                                                                            |
| `discovery`                                         | core  | vitest | `discovery/testing/**/*.spec.ts`, coverage over `discovery/index.ts`.                                                                                                    |
| `artifact-cache-commit`                             | core  | vitest | `artifacts/testing/**/*.spec.ts`, coverage over `artifacts/index.ts`.                                                                                                    |
| `graph`, `content`, `semantic`, `outputs`, `worker` | core  | vitest | The area's `vitest.config.ts`. `semantic` also measures `kernel/*.ts`.                                                                                                   |
| `compiler`                                          | core  | vitest | `compiler/vitest.config.ts` plus `watch.integration.ts` (120 s timeout). Four CI shards.                                                                                 |
| `progress`                                          | core  | vitest | `progress/vitest.config.ts`, with real child processes and PTYs.                                                                                                         |
| `bootstrap`, `vite-adapter`                         | posix | vitest | Host adapters, including the Vite production pipeline, prerender and Vite builders (`vite/testing/{application,prerender,production}.vitest.ts`) and `ng-doc prerender`. |
| `angular`                                           | posix | vitest | Unit tests plus `native-smoke.integration.ts` (real Angular builders in owned child processes).                                                                          |

How the runner behaves:

- **Lanes:** `--lane core` runs only core groups. `--lane posix` runs every group and needs POSIX process groups, so it doesn't work on Windows.
- **Gates:** every coverage group (all except `source-boundaries` and `contracts`) enforces **≥ 90 % lines, statements and functions, and ≥ 85 % branches** over its declared production files. Never exclude production code or add `/* v8 ignore */` to pass a gate; add tests.
- **Log directory:** `--log-dir` is required and **must not exist yet**. The runner refuses to overwrite earlier results. Use a fresh path under the ignored `tmp/`.
- **Execution:** every group runs in its own owned process group, with a timeout (`--timeout-ms`; default 10 min per group, 35 min for `compiler`; `--list` shows each). The run stops starting groups at the first failure, and `results.json` in the log directory records the outcome in plan order. For each failed group the CLI prints the last 200 lines of its `run.log` after the failure line, so a CI job log shows the cause without the artifact.
- **Light and heavy groups:** a group marked `heavy` starts real processes, builds TypeScript programs or measures timing (`session`, `discovery`, `graph`, `semantic`, `compiler`, `worker`, `progress` and every posix group). The light groups run first, up to `--jobs` at a time (default: half the CPUs, at most 4); the heavy groups then run one at a time. `--weight light` or `--weight heavy` selects one kind. On a machine shared with other agents, take the machine's exclusive lock only for the heavy groups: the light core groups (`--weight light`, about 2.5 minutes, most of it `artifact-cache-commit`) need no lock.
- **Shards:** `--shard <index>/<count>` runs one Vitest shard of a single group. A group with `shards` (`compiler`, four CI shards; `vite-adapter`, three) also declares `shardWeights`, its test files' durations in seconds, and its shards are split by weight (`tools/scripts/vitest-shard.mjs`; a file without a weight counts as the median). A shard with coverage writes a Vitest blob report (`<group>/blob/blob-<index>-<count>.json`) and does not gate: the gate applies to the merged shards. `--merge-coverage <dir>` takes a directory holding exactly one blob per shard, replays their results and enforces the thresholds over the merged coverage; it refuses a missing or unexpected blob. Refresh `shardWeights` when a file's duration changes a lot (the per-test durations come from `--reporter=json`).
- **Without coverage:** `--no-coverage` runs the tests only, with no gate and no raw V8 records. The CI Windows jobs use it; Linux measures every gate.
- **Progress layering:** `source-boundaries` also checks that `progress/` imports only its own files, `node:*` (not `node:module`, `require` or `createRequire`) and types from `../contracts`.
- **Kernel leaf:** it also checks that `kernel/` imports only its own files, `node:*` and `../contracts` (ESM imports only). Kernel tests live in `semantic/testing` (for example `canonical-digests.vitest.ts`), whose group gates `kernel/*.ts`.
- **Environment per group:** an entry's `posixEnv` is added to the test environment on every platform except Windows. The `progress` group sets `NGDOC_REQUIRE_PTY=1`, so its pseudo-terminal checks fail instead of skipping when Python 3 is missing. Outside the runner they skip with the reason in the suite name.
- **Self-tests:** after changing the runner, run `node --test tools/scripts/testing/check-builder-modernization.test.mjs tools/scripts/testing/vitest-shard.test.mjs tools/scripts/testing/check-ci-jobs.test.mjs`.

## Fast inner loop

Run a single file with its area's config, then run the full group before you finish.

```sh
node node_modules/vitest/vitest.mjs run --config libs/builder/generator/compiler/vitest.config.ts libs/builder/generator/compiler/incremental.vitest.ts
node node_modules/vitest/vitest.mjs run --config libs/builder/generator/semantic/testing/vitest.config.ts -t "retained"
node node_modules/vitest/vitest.mjs run --config libs/builder/vitest.config.ts generator/session/testing/build-session.spec.ts
```

**Type-check** the area you touched; Vitest does not type-check. Use `node node_modules/typescript/bin/tsc -p <tsconfig> --noEmit --skipLibCheck` with:

| Area touched                                                                 | tsconfig                                                                                                                                                        |
| ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `compiler/`                                                                  | `libs/builder/generator/compiler/tsconfig.json`                                                                                                                 |
| `outputs/`, `vite/`, `angular/`                                              | the `tsconfig.json` in that directory                                                                                                                           |
| `progress/`                                                                  | `libs/builder/generator/progress/tsconfig.json`                                                                                                                 |
| `semantic/`, `worker/`, `bootstrap/`                                         | `libs/builder/generator/<area>/testing/tsconfig.json`                                                                                                           |
| `session/`, `artifacts/`, `discovery/`, `graph/`, `content/`, `contracts.ts` | no config of their own: use `bootstrap/testing/tsconfig.json` and `compiler/tsconfig.json`, which reach them by import. Vitest does not type-check their specs. |

## Writing a new test

- **Start from a neighbour.** Copy the closest existing test in the same area and keep its setup and cleanup pattern.
- **Shared helpers:**
  - `session/testing/support.ts`: a session test harness, a fake `FileEventSource` (`Events`), snapshot and commit stubs, `deferred`/`until`.
  - `compiler/testing/source-bundle.ts`: `bundleSourceCompiler()` bundles the compiler from source for worker/real-process tests.
  - `bootstrap/testing/fixtures.ts`: configuration and snapshot fixtures.
- **Differential tests:** use `compiler/incremental.vitest.ts` as the template. It runs a cold build, the incremental path and the reference path, then compares them.
- **Tests that must hold under load.** The posix groups run many real servers at once, and reviews run them on a loaded machine. Wait for a real signal (the adapter's reload, every hot update handled, a logged error, the served bytes), never for a quiet period or a fixed delay. Give every Vite server of a fixture its own `cacheDir` inside the fixture, below a `node_modules` folder (linters skip it, and an optimizer run that outlives the server may still write there): the default dependency cache below the nearest `package.json` is shared by every fixture, and a parallel server re-optimizing it deletes chunks another serves. Land a multi-file change at once (stage it outside the Vite root and rename it in), and write a watched file with a rename when a test counts its reports: FSEvents may report one write twice, or a creation as a change. On macOS a process group whose members all exited but are not reaped yet answers `kill` with EPERM, not ESRCH. Its fixtures and the targeted arms live in `compiler/testing/incremental-support.ts`, shared with `incremental-targeted-{corpus,seeds,cases}.vitest.ts` and `incremental-partition.vitest.ts`; the suites are split so that they run in parallel shards. A file that uses the support module calls `afterEach(disposeAll)`.
- **Keep files shardable:** a test file runs whole in one shard, so a file that takes many minutes bounds its group's shards (`page-tabs` was split in two for the `vite-adapter` shards, its fixture in `page-tabs-support.ts`). Split a long file along its tests (shared fixtures in a `testing/` module) rather than adding to it, and give the new file a weight in `shardWeights`.

## Tests outside the runner groups

- **Added by the runner:** `compiler/watch.integration.ts`, added to the `compiler` group, and `angular/testing/native-smoke.integration.ts`, added to the `angular` group (it bundles `native-smoke-entry.ts`, which schedules the builders with a real Architect on a small Angular fixture: a build, a dev server with an edit and a stop, and a fatal watcher error; each child must exit by itself).
- **In no group and no CI job:** these must be run by hand when you touch their area, with `node node_modules/vitest/vitest.mjs run --config <config>`:
  - `worker/testing/actual-composition.integration.ts` (`worker/testing/actual-composition.vitest.config.ts`)
  - `testing/service-composition.vitest.ts` (`testing/composition.vitest.config.ts`)

## What a generator change must prove

- **Unit behaviour** in the area's suite, including failure paths and diagnostics codes.
- **Determinism and incremental equality.** Any change to reuse, caching, retention, transport or watch must extend the differential tests. They compare the incremental result against the reference path (`incrementalReuse: false`) and against a cold build, byte for byte. Where they live:
  - `compiler/incremental.vitest.ts` and the targeted arms of `compiler/incremental-targeted-{corpus,seeds,cases}.vitest.ts` (targeted rebuild on, off and a cold build, with the committed tree) and `compiler/incremental-partition.vitest.ts`
  - `compiler/dry-run.vitest.ts` (the targeted rebuild's `verify` mode) and `compiler/targeted.vitest.ts`; their edit corpus (`compiler/testing/targeted-corpus.ts`) designates each edit kind content or full, including page title and data, demo `.ts`, playground, API edits, a guide's live API embeds and the embedded declaration edited, behind a re-export, renamed, deleted and restored (a step may be designated `fails`), and the structural class (pages added, renamed and deleted, categories added, retitled and removed, pages moved between categories, API files joining and leaving a scope, API entries added and removed)
  - `compiler/scoped-semantic.vitest.ts` (scoped semantic invalidation against the switch off, its reference path and cold builds, with the rendered set per edit) and `semantic/testing/program-index.vitest.ts` (closure digests)
  - `compiler/first-edit.vitest.ts` (the first edit after a cold start and after a start restored from the cache, primed as the session primes, compiles targeted: API, page title, demo and guide edits, each byte-identical to the targeted rebuild off and to a cold build; without the store the API, page title and demo edits exceed the dirty threshold and run FULL (the fixture has more API declarations than the unit floor); a restored start after an edit made while the server was down renders only what changed), `compiler/closure-store.vitest.ts` (the closure store's gating, format and header, write skip, stale temporary files and invalid files) and `semantic/testing/closure-seed.vitest.ts` (seeded records hold without recomputation on the previous program, are checked on another, a wrong record never confirms a digest, and shape closures in `verify` mode check a seeded record's type closure)
  - `compiler/fast-start.vitest.ts` (the fast start: a start with nothing changed restores without rendering and equals the switch off and a cold build; guide, API, page module and demo edits made while stopped compile and equal cold builds; a restored start after an edit links only what it reached; compiler, toolchain, option and switch changes reject the record; a damaged or missing cache entry, a damaged, foreign or missing record and an appeared missing directory are never trusted; `verify` reports a differing candidate; only a retaining development runtime records; the first edit after a fast start and its warm-up compiles targeted; `verify` compiles from scratch and reports an input both the record and the cached artifacts lack; another ICU or default locale rejects the record), the locale-independent output order of `compiler/locale.vitest.ts` (one tree compiled and committed in a Swedish and a C process, byte-identical; no `.localeCompare(` in the shipped builder sources), `outputs/outputs.vitest.ts`, `helpers/testing/navigation-title-order.spec.ts` and `helpers/testing/text-order.spec.ts`, and the concurrent unchanged-output checks of `artifacts/testing/commit-fast-path.spec.ts` (the first failure in plan order), and `artifacts/testing/parallel-writes.spec.ts` (parallel writes on and off publish the same tree, manifest and results, with delta commits on and off; the concurrency bound; a staging write, a backup copy or a publish failing mid-batch and an abort, in both modes: the operations in flight settle before the rollback, the first failure in plan order is reported, nothing of the stage is left and the old files are back, untouched where they were not replaced; a failed copy moves its output away right before that output's rename)
  - `compiler/highlight-cache.vitest.ts` (the highlight cache on, off and `verify` in generation chains with a targeted edit and a restart on a warm pack, byte-identical with each other, the reference path and cold builds; production and `cache: false` keep no pack; `verify` reports a tampered pack), `content/testing/highlight-cache.vitest.ts` (every code block of `apps/ng-doc` byte-equal with the cache cold, warm, read from a pack and corrupt; key components; pack failures, sweep and limit) and `libs/utils/html/process-html.spec.ts` (`npx nx test utils`: `processHtml` without a cache is the old pipeline verbatim)
  - `compiler/parallel-render.vitest.ts` (parallel rendering off, on with 1, 2 and 4 threads answering in a random order, and `verify`: chains byte-identical with each other, the reference path and cold builds, memo included; failing pages and failing threads; abort; fronts in plan order and the records journal of a sequential render), `content/testing/html-pool.vitest.ts` (the pool and its failure paths; render threads run a bundled entry, `content/testing/html-thread.ts`) and the runtime cases of `worker/testing/worker.vitest.ts` and `worker/testing/render-threads.vitest.ts`
  - `compiler/shape-closure.vitest.ts` (shape closures on, off, their reference path and cold builds, with the rendered set per edit: an explicit-type body edit, an inferred type, emit diagnostics, a base-class body and a parameter default; `verify`; a cache restored across the switch) and `semantic/testing/shape-closure.vitest.ts` (declaration shapes, own files and heritage, records per mode, a patched program equal to cold)
  - `compiler/type-order.vitest.ts` (union member order: named types of one and of three files, generic instantiations, written and inferred literal unions, a reordered alias no page reads, and file-order changes of named types, of unnamed types of two workspace files, of a library file, of a global declaration file, of library-internal files and of files behind a global-scope module, and members that tie on every key but the type id, bare or wrapped (a type reference, a mapped alias, an intersection, a property, a parameter, a return), and two guides documenting a declaration outside the program, each byte-identical with every switch on, off, the reference path, `verify` and cold builds; a fragment outside the program; playground options in written order on every path), `helpers/testing/written-union-order.spec.ts` (written-order options) the file-order swap detection of `semantic/testing/program-index.vitest.ts`, the canonical printed order of `semantic/testing/type-text.vitest.ts`, and the persisted order of `compiler/closure-store.vitest.ts` and `semantic/testing/closure-seed.vitest.ts`; the mutated-program arm of `compiler/incremental-targeted-cases.vitest.ts` fails if a fragment's addition reorders the files
  - `compiler/tracked-program.vitest.ts` (whole-program tracking reuse on and off: production and unscoped development generations track each program once, byte-identical to the switch off and to a cold build)
  - `compiler/retained-program.vitest.ts` (with the incremental program's patched arms: on, off, a syntax error and its fix, a superseded patch)
  - `semantic/testing/retained-program.vitest.ts` and `semantic/testing/program-patch.vitest.ts` (a patched or restructured program equals a cold synchronization: observations, root names, file order and texts, CRLF and byte order marks, inherited documentation; entries added, moved and removed, API scope files added and deleted, changed imports) and `semantic/testing/program-verify.vitest.ts` (`verify` catches a stale checker cache)
  - `worker/testing/{delta-transport,retention,commit-race,priming}.vitest.ts`; `priming.vitest.ts` also runs the startup buildOnce in the long-lived runtime, whose warm-up compiles nothing, and an edit sent right after the watch starts, which must take the retained-program skip (the other first-edit tests wait for the warm-up)
  - `vite/testing/structural-pass.vitest.ts`, the structural pass arm of `vite/testing/startup-native.vitest.ts` (a tab route edit takes one Analog pass with `NGDOC_ANGULAR_STRUCTURAL_PASS` on and at least two off, and both serve the same modules; its description-module arm counts the passes of a page added, a failing page, a category without pages, an existing description module replaced by an add-only event and a page deleted) and the structural corpus of `vite/testing/page-tabs-structural.vitest.ts` (a page added, renamed, retitled and deleted and a category added, each update equal to a cold build, on and off)
  - `session/testing/delta-transport.spec.ts`
  - `discovery/testing/determinism.spec.ts` and `discovery/testing/partition.spec.ts` (the configuration/entry partition, the `evaluated` digest, and code-unit dependency order in the one digest domain)
  - `semantic/testing/canonical-digests.vitest.ts` (the digest domain: canonical JSON, code-unit order, every reader's content digest equal to the refresher's, byte order marks and invalid UTF-8)
- **Progress.** Host progress wiring has tests in each host's group: `session/testing/progress.spec.ts` (event order, triggers, counts, supersession, activities, a failing consumer, results equal with and without a consumer), `bootstrap/testing/cli-progress.vitest.ts` (stderr and stdout, order after diagnostics, `--json`, live, foreign after a host spawn, no `WORKER_ABORTED` error for Ctrl-C or a superseded edit), `vite/testing/progress.vitest.ts` and the real server and build cases in `vite/testing/vite-adapter.vitest.ts` (summary before the banner, a timestamped line per edit, one generation for the builds of a production pipeline that share its handoff), the `NgDoc progress` block of `angular/testing/angular-adapter.vitest.ts`, `progress/testing/gate-host.vitest.ts`, and the real-process cases of `progress/testing/harness.vitest.ts` (PTY runs: Nx pane widths, a single Nx task, Ctrl-C, SIGTERM and SIGHUP while the live line shows, Ctrl-C with a host SIGINT handler). Compilation phases: `compiler/progress.vitest.ts` (phase order, totals equal to the loops, the targeted pass and its fall back, nothing from the `verify` oracle, results byte-identical with and without a consumer) and `worker/testing/progress.vitest.ts` (coalescing, `boot` and `transfer`, dropped malformed, foreign and pre-ready messages, nothing after an abort, no progress for a warm-up). Host test harnesses that clone bootstrap options must leave `session` out: `onProgress` is a function.
- **Dependencies.** A new read has a test showing that editing that input triggers a rebuild of exactly its consumers.
- **Real processes.** Worker, watcher, host and SSR changes need real-process tests (the posix groups) in addition to mocked ones. Mocked integration is not proof that a real Angular/Vite pipeline works.
- **Production completeness.** Production still emits and validates every page.

## End-to-end acceptance

The harnesses under `libs/builder/generator/acceptance/` consume the **built** package in `dist/libs/builder`. For example: `native`, `production`, `vite-main`, `ssr-lifecycle`, `edit-chains`, `package-consumer` and `package-optional`. Run `ls libs/builder/generator/acceptance` for the full list.

Build first (see [repo-and-commands.md](repo-and-commands.md)), and follow the `dist` rules in [agent-safety.md](agent-safety.md).

- **Browser harnesses:** these need `PLAYWRIGHT_MODULE` and `CHROME_PATH`.
- **Options and output:** read the harness's `run.mjs` (and its README where present) for its options. Most write their results to a directory passed through an environment variable; without it, they default to `tmp/acceptance/<harness>`, which Git ignores.
- **Inputs:** a harness reads only the repository sources, its own committed fixtures (for example `production-c/baseline-routes.json`) and what the same run or CI job produced. A script that reads an earlier step's output fails with a message naming that step when it is missing. Nothing under `libs/`, `tools/` or `.github/` may reference `docs/architecture`, which is not part of the published repository; `tools/scripts/testing/internal-docs-boundary.test.mjs` enforces this.
- **Cost:** they are slow, so run the one that matches your change rather than all of them.
- **Packed `ng add` and `migrate-to-vite`:** `acceptance/ng-add-e2e` packs the built package set (`dist/libs`, including `add`), serves it under its own names from a local registry for the `@ng-doc` scope, and runs two scenarios in fresh applications made by `ng new`: `ng add @ng-doc/add` (Vite engine), and the legacy builders migrated with `ng g @ng-doc/builder:migrate-to-vite`; each then runs `ng build` and an `ng serve` smoke that fetches the docs page and its generated module. It runs on Linux, macOS and Windows and needs the npm registry. Harness tests: `node --test libs/builder/generator/acceptance/ng-add-e2e/harness.test.mjs`; scenarios: `node --test libs/builder/generator/acceptance/ng-add-e2e/scenarios.e2e.mjs` (`NGDOC_NG_ADD_E2E_EVIDENCE`, `NGDOC_NG_ADD_E2E_NPM_CACHE`, `NGDOC_NG_ADD_E2E_KEEP=1`; `--test-name-pattern "^scenario A"` runs one), or `run.mjs --scenario a|b`. Each scenario has a 28-minute budget that cuts every command's timeout, cancellation and SIGINT/SIGTERM stop its processes and remove the workspace, and it asserts that every installed `@ng-doc/*` package is the packed tarball from the local registry.
- **Mutation testing:** `acceptance/mutations/run.mjs` applies known mutants (needle/replacement pairs) to generator sources in a temporary copy and checks that the scenarios kill them. If you edit a line that a mutant targets, update its needle in the same change.
