# The generator engine (`libs/builder/generator`)

The generator is the new documentation compiler. One engine serves every host:

- a standalone CLI;
- a Vite/Analog plugin, which the Angular CLI builders `vite-application` and `vite-dev-server` run from a Vite configuration.

It turns a docs tree (config, pages, categories, API scopes, markdown, Nunjucks, demos, playgrounds) into generated Angular sources, assets, search indexes and keyword maps.

The engine is still evolving. This file describes its lasting architecture and invariants. When you change them, update this file too.

The layering is enforced:

- **Private Angular CLI imports:** these (`@angular-devkit/build-angular`, `@angular/build`, `@angular/cli`, compiler-cli internals, ...) are forbidden in the core directories. The core is `artifacts`, `compiler`, `content`, `discovery`, `graph`, `outputs`, `semantic`, `session`, `worker` and the root contract files. The `source-boundaries` runner group checks this. Only the `vite/` and `bootstrap/` adapters may touch host APIs.
- **Legacy code:** the runtime (`compiler`, `bootstrap`, `worker`) must not bundle the legacy engine (`libs/builder/engine`, `application`, `dev-server`, `libs/builder/index.ts`). `build-generator.mjs` fails the build if it does. The shared pure pieces `libs/builder/{helpers,parsers,types,templates}`, `libs/core` and `libs/utils` are allowed.

## One generation

`CompilationService.compile(request, signal, context)` (`compiler/index.ts`) runs these phases in order. An error diagnostic ends the attempt.

1. **Discovery.** Produces the `DiscoverySnapshot`.
2. **Semantic.** `synchronize` builds the TS program, or reuses a retained one. It fails with `SEMANTIC_OWNED_ROOT_OVERLAP` when a program input lies under the output or cache root.
3. **Setup** (`planGeneration` in `plan.ts`). Sets up the previous snapshot, reuse facts, cache and memo.
4. **Describe** (`describe.ts`). Produces units: one page shell, one category, or one unit per API declaration, each with content descriptors.
5. **Plan and render** (`planContent` in `plan.ts`, `render.ts`). Every descriptor is rendered into a `ContentIR`; an unchanged descriptor with unchanged refreshed dependencies reuses the previous IR.
6. **Keywords and link** (`link.ts`). Keywords are combined in the order remote, configured, then local exports; the last one wins. A name exported twice with different targets is a `KEYWORD_DUPLICATE` warning, except for a name defined in `keywords.keywords`: when its url is the route of a local export of that name, that export wins silently; otherwise it replaces the loader keywords silently and a local export still wins with the warning. A configured internal url that replaces a loader keyword when no local export of the name is left, and that no entry or local export of the build has as its route, is `KEYWORD_PIN_UNRESOLVED`. Discovery leaves out configured keywords without a url (`DISCOVERY_KEYWORD_INVALID`). A strict index-completeness check runs before linking: a descriptor without its IR fails the generation.
7. **Assemble and aggregate** (`assemble.ts`). Produces page artifacts and outputs, plus site-level routes, search and the API list. This step builds the candidate `ArtifactSnapshot` and writes the cache.
8. **Validate and fold** (`fold.ts`). Every phase writes its diagnostics and dependencies into per-unit records. Every exit builds its `CompilationResult` by replaying them phase-major, in unit plan order. Never push into shared accumulators; that would break determinism.

Then the session commits the candidate through the `OutputCommitter`, and the host (Vite, Angular or the CLI) publishes the result.

### The targeted path (`compiler/targeted.ts`)

A development watch generation of a long-lived runtime (it retains a program) may compile only what its content, page, program and structural edits reach. It still runs discovery and the semantic synchronization, then:

1. **Before discovery**, the change set is the request's changes, plus the changes of every generation against the same base that did not commit (failed, aborted or discarded; kept on the retained entry), plus the paths a stat sweep of the base's recorded observations finds changed. `compiler/classify.ts` classifies each path by its current state against the base's reverse index (`graph/unit-index.ts`), which keeps a set of roles per path (a page module is usually a program input too). The targeted path may take:

   - `content`: a path a unit recorded;
   - `entry`: an existing page or category module, or an input of an entry's evaluated closure;
   - `semantic`: an existing program input whose change moves no program glob, only while the generation records semantic closures (`NGDOC_SCOPED_SEMANTIC` on; an `entry` path that is also a program input needs them as well);
   - the **structural class** (`PathClassification.scoped`), with the same condition: a description module, entry input or observed markdown file that no longer exists, a discovery glob or program glob (an API scope, the tsconfig include) whose membership changed, a deleted program input, an ancestor directory of a recorded path, and an unknown path when the pass also has an entry, program or structural path. Each unknown path must then be read by the generation's fresh discovery, its program or a unit it rebuilds (`TargetedGeneration.explain`); otherwise the attempt goes FULL.

   Everything else goes FULL: program and output configuration, the configuration's inputs, the header template, a content-level glob a unit recorded, and an unknown path alone. The candidates are the units that recorded a changed path.

2. **After setup**, the fresh-discovery check: the configuration, the `onlyForTags` exclusions and the output templates must equal the base's; a reused program must also have the base's program dependencies. The entry set may differ (`discoveryChanges(…, structural)`): an entry the base does not have is described, the units of an entry it no longer has are dropped (their exports join the keyword diff, their edges leave the index), and an entry whose kind changed is described again (its units change identity). Unit order follows the fresh discovery, as on the full path. Then these entries become candidates (all of their units):

   - every entry whose descriptor changed in any other way (title, route, order, data, markdown files and digests, closure inputs, the `evaluated` digest): a unit's describe, render and assembly read only its own entry, and the site-wide outputs, which read every entry, are aggregated in full;
   - the entry of a replayed unit whose refreshed non-physical dependency changed: its `evaluated` digests against the fresh discovery and, when the program is not provably the base's (`closuresHold()` is false: the program was patched or synchronized again, for example after a page, demo or playground `.ts` edit), its semantic closures and references against the current program, as the full path's reuse predicate does;
   - a guide whose live values (`readGuideValues`) changed.

   **API declarations** are candidates one by one; their entry is described declaration by declaration (`TargetedGeneration.describing`, `DescribePlan`). Whenever the program is not the base's, the entry set or an entry changed, or an API unit is a candidate, every API entry is enumerated again in entry order (enumeration reads the program's scopes and every entry's route, and a disambiguated route must avoid the earlier entries'), and `describeEntry` takes that enumeration instead of enumerating again. The entry's own unit is replayed while its enumeration contribution (its first describe record) is unchanged; a declaration unit is replayed while its descriptor is equal and it is no candidate; new declarations are described and dropped ones removed. An API entry whose descriptor changed is described in full (its units' input digests hold the entry).

   A generation without semantic closures (`NGDOC_SCOPED_SEMANTIC=0`) admits only a reused program and no structural change. The dirty threshold and a digest conflict found after render go FULL. When the entries or the program changed, the retained index builds its roles, observed-markdown owners and globs again.

3. Candidates run the full path's own describe, render (with its reuse predicates), link and assembly code. Every other unit is **replayed** from the retained records of its base (`RetainedBuild`): what the full path would record for it, and its previous artifact. The keyword set is combined in full; the one-hop consumers of every key whose binding changed are linked and assembled again. The aggregate, the output existence scan over every previously published output, validation and the fold run as in the full path.
4. Any error of the targeted attempt re-runs FULL in the same generation.

**Keyword loaders are pinned on the targeted path.** When the path pass (step 1) allows a targeted attempt, discovery does not invoke the `keywords.loaders` (network and local alike): each loader whose `loaderId` has a result in the base's retained build reuses it (`DiscoveryRequest.pinnedRemoteKeywords`); any other loader is invoked. A generation that then publishes anything but a targeted result (the equality check or the targeted attempt goes FULL, or a phase fails) first runs discovery again without the pin, keeping the program when the configuration and entries are unchanged and synchronizing it again otherwise. So loader results refresh on every FULL generation and on restart, never while only content is edited, and not on a targeted structural change either (a page added, renamed or deleted keeps the pinned results). Production, one-shot generations, `NGDOC_TARGETED_REBUILD=0` and the reference path never pin. `verify` compares with the pinned results, so a changed remote result is not a mismatch; after a `verify` mismatch the published FULL result keeps the pinned loader results (a diagnostic mode only).

### The fast start (`compiler/fast-start.ts`)

A development start (a `buildOnce` without a previous snapshot or changes, `fastStartMode`) whose recorded inputs all re-read identically publishes the recorded candidate without building the program or rendering, linking and assembling anything (the `restore` phase, pass `restored`: `NgDoc: OK restored …`).

- **The record.** Every development generation that writes the cache in a runtime that retains its program also writes `<hash(projectId)>.fast-start.json` beside it (best effort, atomic, skipped when this process last read or wrote the same bytes): a header (the record version, `GENERATOR_SCHEMA_VERSION`, every compilation option, every engine switch but `NGDOC_FAST_START` as read when the compilation service was created and when it compiles, and `runtimeIdentity`: the Node, ICU and Unicode versions, the default locale, ts-morph's TypeScript version and the resolved `package.json` versions of the packages that shape output), the candidate's revision, the digest of the generation's discovery (the snapshot and the discovery contributions), the result's dependencies and diagnostics, and the program's private observations (`ProgramWatchFacts`: the `types` directives' reads, the missing directories, the symlink real paths and the type root listings; glob listings are left out, since the check observes every glob again in full). A one-shot runtime retains no program, so it writes none.
- **The check.** Discovery always runs (user modules are evaluated, keyword loaders refresh). The record is taken only when the header and the discovery digest are equal; every recorded content (by the digest of its bytes, never a stat), existence and glob membership (outside the owned roots) and every private program fact re-reads identically; the cache index restores every artifact of the recorded candidate (`snapshotOf` gives the recorded revision); and each artifact is `intact` (its revision is the digest of its body). The program a synchronization would build is then the recorded one, so every semantic digest the candidate holds is current, and the result's dependencies are exact. Anything else is a reason (`fast start: <path> changed`, `… the engine, its options or its switches changed`, …), reported as the full pass's reason, and the generation compiles as without the fast start.
- **The result** is the recorded candidate with the recorded dependencies and diagnostics and an empty `whyRebuilt`. A result is history-dependent beyond its candidate (a reused IR emits no render diagnostics), as it already is between a cold and a restored start; the candidate and the published output are byte-identical to compiling. The startup commit is the full commit, so outputs changed while the server was stopped are repaired.
- **The warm-up** then builds the program: the session primes the long-lived runtime as after any reused baseline, and since that runtime retains nothing after a fast start, the warm-up compiles in full in the background. An edit made before it ends stops it, as any edit does, and that edit's generation is FULL once (a warm-up that finished after the edit changed the tree would have built the program of a candidate that is never committed).
- **A start after edits** (the check failed) compiles with the cache index as its previous artifacts, and reuses their links, assemblies and revisions like a session snapshot's (`GenerationPlan.sessionPrevious`, `restoredReuse`) when every restored artifact is `intact`.
- `NGDOC_FAST_START=0` (`CompilationOptions.fastStart: false`) turns off both; `verify` restores, then compiles from scratch (the reference path's options, no previous artifacts: not even the cache index, no memo, no closure store, no restored reuse), publishes that result and reports `COMPILATION_FAST_START_MISMATCH` when the candidates differ, so it also catches an input that both the record and the cached artifacts lack.

The retained build and index belong to the retention entry (committed/working lifetime). After a targeted generation the index is an overlay of the base's; after a FULL one it is built again. **The first edit after a start:** the startup generation is a development `buildOnce` (cold, or restored from the cache). With warm-ups allowed (`NGDOC_PERSISTENT_WORKER_PRIME`) the worker serves it, while no watch has run yet, in the long-lived runtime (`worker/index.ts` `servesStartup`), which keeps its retained build, index and closure records for the committed revision; the warm-up the session then asks for (`PrimingCompiler`) finds that entry and returns without compiling (`worker/entry.ts`), so an edit right after the start takes the targeted path. A warm-up that compiled instead took about as long as a full generation, and an edit arriving meanwhile aborted it (or, when it waited, the warm-up read the edited tree and was stale) and rebuilt every page. Such a build reports no pass in its progress, like one in a one-shot runtime. Without warm-ups the startup generation runs in a one-shot runtime and leaves nothing; a warm-up that compiles (for example after the runtime was recycled) is a FULL generation that builds the retained build and index and takes the closure records from the closure store (below), so the first program edit refreshes the replayed units' closures instead of finding every one changed and exceeding the dirty threshold. Production (`buildOnce`), one-shot generations and the reference path never take the targeted path. Only a targeted result may be committed as a delta (`CompilationService.targetedResult`); the session gives every other generation the full commit.

### Cached highlighting (`content/highlight-cache.ts`, `libs/utils/html/plugins/cached-shiki.plugin.ts`)

`processHtml` (`@ng-doc/utils`) takes an optional `highlight` cache. Without it (the legacy engine, `NGDOC_HIGHLIGHT_CACHE=0`, the reference path) it runs the plain `@shikijs/rehype` plugin, which sets its highlighter up again (every bundled language and both themes) for every document. (With `grammars: 'used'`, below, both paths highlight with `@shikijs/rehype`'s transformer over a per-thread highlighter that loads only the grammars blocks reach.) With it, the generator's path:

- **The plugin** selects the blocks exactly as `@shikijs/rehype` does and keys each without changing the tree. A miss is highlighted by `@shikijs/rehype`'s own transformer on a tree holding only that block (so options, language fallback, meta parsing and transformers are the plugin's), created once per thread and theme pair; a transformer whose highlighter failed to load is forgotten. Values are serialized before any splice and every block gets nodes parsed afresh, since later plugins mutate the tree. A failing block rethrows the plugin's error at the same block and nothing is stored. `@shikijs/rehype` replaces a block with the root of the highlighted fragment, so a value is a JSON array of HAST elements or of such roots; anything else is a miss. A document whose blocks all hit (or that has none) never loads Shiki once the cache proves its themes load (`loads`: the cache holds a block highlighted with them), so a theme that cannot load still fails every document, as before.
- **The key** is `digestOf({ context, block })`: the context covers the pack version, the resolved versions of `shiki`, the Shiki packages it highlights with (`@shikijs/core`, `@shikijs/langs`, `@shikijs/themes`, `@shikijs/engine-oniguruma`, `@shikijs/vscode-textmate`) and `@shikijs/rehype` (`SHIKI_PACKAGES` from `runtimePackages`) and each theme's identity (a bundled theme's name; NgDoc's theme by the digest of `ngDocSyntaxTheme()`); the block the plugin's format and fixed options (`HIGHLIGHT_IDENTITY` in `process-html.ts`: bump `format` with any change to the options or the plugin), the theme names, the language before its fallback, the raw meta string and the text.
- **Extra languages.** `shiki.langs` (discovery copies the registrations as plain JSON into `GeneratorConfiguration.shikiLangs`, absent without any, and fails with `DISCOVERY_SHIKI_LANGUAGE_INVALID` otherwise) reach `processHtml` as `langs` through render tasks and warm-ups. With them, both highlighting paths use a highlighter of their own per thread, themes and languages (every bundled language, then the registrations, so a registration replaces a bundled language of its name), never `@shikijs/rehype`'s process-wide singleton: other languages in the same process can't change a block's result. The languages enter the cache context (a digest) and each block (`languages`).
- **Used grammars.** Setting a highlighter up with every bundled grammar takes seconds, so the generator passes `processHtml` `grammars: 'used'` (both paths, unless `NGDOC_USED_GRAMMARS=0`): one highlighter per thread and theme pair starts without languages, and before a document is highlighted it loads the closures of the document's block languages (`libs/utils/html/shiki-grammars.ts`: embedded and lazily embedded languages, included scopes, injectors by scope prefix and every injector sharing a target with one in the set), in the order loading everything registers them. A highlighter grows only by whole closures, so a block's HTML is the one every grammar gives, whatever was loaded before; `process-html.spec.ts` checks every bundled language in shuffled orders against the plain plugin. A render thread's warm-up highlights TypeScript, Angular TypeScript and Angular HTML, so their grammars (Angular HTML reaches about 90) load during the semantic phase. With `shiki.langs` every grammar is loaded.
- **Storage.** One map per runtime (thread), kept across generations by a long-lived runtime and cleared when it outgrows `HIGHLIGHT_CACHE_LIMIT` (64 MB). Development generations with the artifact cache read `<hash(projectId)>.highlight.json` beside it once per runtime and context (another version or context, unparsable JSON or a non-string entry: not read) and write it after the cache (best effort, atomic, stale temporaries swept, skipped when the same keys are still on disk and no entry was replaced). A generation that rendered every content writes exactly the keys it used; one that reused or replayed some (targeted, IR reuse) keeps the earlier keys too, unless that would exceed the limit. Production, `cache: false` and the fast start's `verify` scratch compile never read or write the pack (production uses the map only); the reference path uses no cache.
- **No dependencies.** The output is a function of the key, so no dependency, fingerprint or watch input is added. Entries are plain strings: a render thread is handed them (`highlightJournal`, all after a clear, then the new ones) and returns what it hit and highlighted, which the main thread merges in plan order (`HighlightSession.merge`). Only the main thread reads and writes the pack.
- **Tests:** `libs/utils/html/process-html.spec.ts` (the call without a cache is the old pipeline verbatim; cold, warm, corrupt entries, failures, a theme that cannot load, no highlighter for an all-hit document, one highlighter per theme pair, `verify`, a slow clock), `content/testing/highlight-cache.vitest.ts` (every code block of `apps/ng-doc` cold, warm, from a pack and from a corrupt pack; key components; pack failures, sweep, limit, `verify` through the content compiler) and `compiler/highlight-cache.vitest.ts` (chains on, off and `verify` byte-identical, equal to the reference path and cold builds; production and `cache: false` keep no pack).

### Cached formatting (`content/format-cache.ts`, `helpers/format-cache.ts`, `semantic/formatting.ts`)

`formatCode` (`helpers/format-code.ts`, shared with the legacy engine) formats API signatures (`helpers/presentation.ts` through the API templates) and demo snippets (`snippetsFromAsset`) with `@prettier/sync`, and resolved the Prettier configuration again for every call. It consults the cache installed with `withFormatCodeCache` (`helpers/format-cache.ts`, not exported from the package barrel); without one (the legacy engine, `NGDOC_FORMAT_CACHE=0`, the reference path) it is the old code path verbatim.

- **Installation.** `planGeneration` creates the generation's `FormatSession` (`createFormatSession`, on the same terms as the highlight session) and hands it to `semantic/formatting.ts` (`useFormatCache`); the semantic service wraps its two formatting call sites (`fragments.ts`, `angular.ts`) in `formatting(…)`, and the compile's `finally` clears it. Both call sites are synchronous, so the cache is installed exactly for their `formatCode` calls.
- **Configuration.** One session resolves a directory's configuration once. Its files (`FORMATTER_CONFIGURATION_FILES` in the workspace root and every directory above it) are program inputs of every page that formats (`trackFormatterConfiguration`), so an edit runs a new generation, which resolves again; no dependency is added.
- **The key** is `digestOf({ context, parser, config, code })`: the context covers the pack version (bump it with any change to `formatCode`'s options or result handling) and the resolved `prettier` and `@prettier/sync` versions; `config` the resolved configuration's strict canonical JSON with the version of every plugin it names (resolved from the directory). A configuration that is not exact (a value JSON cannot hold, a plugin given as a path or object, or one that does not resolve) is never cached.
- **Entries** are `=` followed by the formatted code, or `!` for code Prettier rejects with a `SyntaxError` carrying `loc` (bare signatures such as `constructor(…): T;` always are): a hit throws again, so `formatCode` returns the code unformatted as before. Any other error stores nothing. An entry of another shape is a miss.
- **Storage.** One map per runtime, kept across generations, cleared beyond `FORMAT_CACHE_LIMIT` (16 MB). Development generations with the artifact cache read `<hash(projectId)>.format.json` beside it once per runtime and context, and write it after the cache and the highlight pack on the same terms (a complete generation keeps exactly its keys; atomic, best effort, skipped when unchanged; a session that formatted nothing leaves it alone). Production, `cache: false` and the reference path never read or write it.
- **`verify`** resolves and formats every hit again, uses the fresh result and reports one `CONTENT_FORMAT_CACHE_MISMATCH` warning (the `aggregate` phase) with the number of differences.
- **Tests:** `content/testing/format-cache.vitest.ts` (`formatCode` with a session equal to without one, cold, warm, from a pack and a damaged pack; one resolution per session; `verify`; exact identities and plugins; syntax errors; keys; pack terms and limit; the switch) and `compiler/format-cache.vitest.ts` (chains on, off and `verify` byte-identical, equal to the reference path and cold builds, `.prettierrc` edits formatting again; a restart with the pack formats nothing and resolves once; production and `cache: false` keep no pack; `verify` reports a tampered pack), and `semantic/testing/formatting.vitest.ts`.

### Parallel rendering (`content/html-pool.ts`, `content/html-pipeline.ts`, `content/html-worker.ts`)

A compile has a **front** (descriptor checks, file reads, Nunjucks with live user values, every semantic query) and a **back** half, the HTML pipeline of `@ng-doc/utils` (`processHtml`, `postProcessHtml`; for a link `replaceKeywords`, `removeNotIndexableContent` and the search records). The back is a pure function of the HTML and JSON values the front produced (`html-pipeline.ts`): it reads no file, program or user value and records no dependency. A large generation runs it on up to four `worker_threads` of the compiler runtime:

- **Fronts stay sequential, settles stay in order.** `GeneratorContentCompiler.compileStaged` resolves once the front is done and the back is dispatched (the rest of a compile after the pipeline is pure); `compile` is `compileStaged` followed by its `finish`. `renderUnits` runs every unit's front in plan order, so the semantic queries and the checker history are a sequential render's, and settles each unit (records, IRs, dependencies, input digest, progress) in plan order once its back halves are done, with at most `4 × threads` units waiting (`RenderBack.window()`). A demo-assets IR reads every asset in its front and processes them in one task, stopping at the first failure; its records replay the one-asset-at-a-time order. `linkUnits` dispatches the links that will not be reused a window of units ahead (`prepareLink`) and still takes, records (`memo.recordLink`, `consulted`, `explainFilteredKeywords`) and reports every result in unit order. Without threads the window is 0: every compile ends before the next starts and every unit settles before the next front, as before.
- **Where tasks run** (`RenderBack`, one per generation): never on the targeted path (`runPhases` admits only the full path) or the reference path; in a generation, the first `PARALLEL_RENDER_THRESHOLD` (32) tasks run in the main thread. A production build or a start without a previous snapshot, of at least `PRESTART_ENTRIES` (16) entries, starts the threads before the semantic phase (`prestartRenderThreads`, after the fast start's check), warmed up with the generation's themes; other generations start them when they pass the threshold, so a small site never starts one.
- **Transport.** Every message is `encode`d JSON text (`worker/protocol.ts`). A render task carries its documents and themes, and the highlight cache's context and `verify`; the thread receives the main thread's highlighted blocks first. A link task carries the IR's HTML, title, route, breadcrumbs and page type; the generation's frozen keyword set crosses once per thread (`keywords`), named by its number. Replies are validated. Every render task of a `RenderBack`, on a thread or in the main thread, records its highlighting per document (`recordingHighlight`) instead of writing the shared cache; the records are merged in submission (plan) order (`HighlightSession.merge`), and only then does a document know which `verify` differences it reports (a difference counts only while the cache still holds the old value), so the cache, the pack and the `CONTENT_HIGHLIGHT_CACHE_MISMATCH` warnings are a sequential render's.
- **Failures.** A thread that cannot start, crashes, exits, replies with something malformed or to no job, or fails a job: its tasks run again in the main thread through the same pipeline, and the rest of the generation runs there. No diagnostic is reported (a cold build has none); `renderPoolCounters` counts it for tests. An abort settles every waiting task as aborted at once (`CONTENT_ABORTED`); a reply after it is ignored.
- **Lifetime.** The pool (`htmlPool`) belongs to the runtime. A long-lived runtime (`worker/entry.ts`, `keepRenderThreads`) keeps it across its generations' services and terminates it before it exits (dispose, recycle); a one-shot compile terminates it when its service is disposed, and the one-shot runtime again before it replies. Threads are unreferenced, add no process listener and change no environment, so `isolate()` is unaffected, and they die with the runtime's process on every other path. A pool without work for 30 s terminates its threads; every start, job and reply starts that time again, and a running compile holds the pool (`holdHtmlPool`), so threads started before a long semantic phase are still there for its render. The thread entry is the bundled `content/html-worker.js` beside the compiler bundle (`GENERATOR_ENTRY_POINTS`); without it (the sources in a test) everything runs in the main thread. The `source-boundaries` check keeps the thread files to the pipeline, the digest, the protocol, `@ng-doc/utils`, `@orama/plugin-parsedoc` and `node:worker_threads`.
- **Size.** `CompilationOptions.renderThreads` (default `min(4, availableParallelism() − 2)`; `0` uses none). Threads count toward the runtime's resident set, which the recycle bound checks.
- **Tests:** `content/testing/html-pool.vitest.ts` (thread results equal the main thread's with 1, 2 and 4 threads in a random completion order; the highlight cache and pack equal the main thread's; `verify`; a thread that throws while loading, exits mid-task, fails, replies malformed or to no job; a missing entry; abort; dispose waits for every thread; idle teardown; non-JSON payloads; the job server in-process), `compiler/parallel-render.vitest.ts` (chains off, on with 1, 2 and 4 threads and `verify`, byte-identical with each other, the reference path and cold builds, memo included; failing pages; failing threads; abort; nothing outlives a one-shot compile; fronts strictly alternate in plan order and the records journal equals the sequential one) and the runtime cases of `worker/testing/worker.vitest.ts` and `worker/testing/render-threads.vitest.ts`.

### Scoped semantic invalidation (`compiler/semantic-closure.ts`, `compiler/closure-store.ts`, `semantic/semantic-closure.ts`, `semantic/program-index.ts`)

In a development generation (production keeps today's format), every semantic query (`enumerateApi`, `describeGuide`, `entry-doc`, `renderFragment`) records one `semantic-closure` dependency, `{ scopeId, key: <scope kind>:<key>, digest }`, in place of the whole program's `semantic-reference`. Units no longer carry that reference, and `compact` keeps the program files a unit read. So an API edit re-renders only the IRs whose closure changed, on a FULL-synchronized program too.

- **The digest** (`ProgramIndex`, one per `ts.Program`, computed with recording suspended) is `H(env, [(f, content(f), typeClosure(f)) for f in R], [(class, derived list)])`. `R` is the query's recorded footprint. `typeClosure(f)` follows each imported name through its alias chain (the export surfaces of the modules on it, then the declaring files' closures, SCC-condensed); other module references take the module's surface and every export's provider. `env` holds the TS version, the options, the global observations other than program files and globs, and the content of every global-effect file (declaration files, scripts, `declare global`, ambient `declare module`). The derived-class lists come from `recordDerivedQuery` in `withIndexedDerivedClasses`, which records only the class and runs the reference search with recording suspended: a search records whatever TypeScript resolves for the first time, so `R` would depend on render order.
- **Shape closures** (`NGDOC_SHAPE_CLOSURE`, on by default). With them the digest takes `shapeClosure(f)` in place of `typeClosure(f)` for every file of `R`; `content(f)`, the file dependencies and the derived lists stay. What a query read of a file itself (initializers, parameter defaults, bodies, comments) is covered by that file's content, and only the files it merely depends on are followed by shape, so soundness rests on the recorder putting every file a query reads into `R`, and on a declaration shape stating everything an importer's types take from its file. `dtsShape(f)` is the isolated declaration emit (`ts.transpileDeclaration`, comments removed, given the program's strictness, target and decorator options: TypeScript's defaults are not the program's) plus the file's enum declarations (the isolated emit drops initializers it cannot evaluate); a file the isolated emit reports a diagnostic for (a type only the checker can state), and every file that is not a TypeScript module source, takes its `token` instead, so it narrows nothing. It is a function of those options and the file's name and text, memoized across programs, and never touches the checker (no history). `shapeClosure` is `typeClosure` over shapes: `dtsShape`, the shape surfaces (`exportSurface` with `dtsShape` for `token`) of the modules on each name's chain, and the providers' shape closures. So a body edit that keeps every declaration shape (for example an explicit-type function body in `libs/core`) changes only the closures whose `R` holds the edited file. Shape-mode keys end with `@shape`: a digest of the other mode never holds without a record (a cache restored across a switch change re-renders). In `verify` the records also keep each query's type-closure digest.
- **`R` must be a function of the program.** A closure recorded in one generation is compared with a fresh render in another, so anything that records history-dependent reads (first-call caches of the checker or the language service) breaks `verify` and the byte equality with a cold build. `NGDOC_SCOPED_SEMANTIC=verify` on `apps/ng-doc` is the audit for it.
- **Union member order must be a function of the program.** Without `stableTypeOrdering` TypeScript orders a union's members by the creation order of their types, and creates a type the first time anything asks for it, so an IR rendered without the pages a cold build renders before it could print `B | A` where the cold build prints `A | B`. `buildProgram` sets `stableTypeOrdering` (TypeScript 6): union members are ordered by kind, name and value, and unnamed types (functions, object types, enum literals, unique symbols) and object-type properties (`getNamedMembers`) by declaration position and the program position of the declaring file. Output then depends only on the relative order of the files that declare the compared types, and adding or removing files reorders no surviving file. The retained closure store keeps its program's file order (`programOrder`); when two files both programs have swapped places (`sameRelativeOrder`: an import or root change that moves a loaded file past another), no closure recorded before refreshes as held, so every unit whose content read the program renders again; with insertions and removals only, file order invalidates nothing. The persistent closure store (`compiler/closure-store.ts`, schema 2) keeps the order with its records; a store without one, or a fresh runtime's empty one, confirms a closure only while the program equals the previous candidate's (same inputs, same order). Members that tie on every key but the type id (object types without a symbol, an alias or a reference target, such as reverse-mapped types, and every type that wraps them: `Holder<R1> | Holder<R2>`, `M<R1> | M<R2>`, `(R1 & Tag) | (R2 & Tag)`) print in the order of their text: `semantic/type-text.ts` wraps the checker's `typeToString`, through which every printed type goes (ts-morph `Type.getText`), on every new checker (at each query and after a fragment re-creates the program). While a type prints, every union and intersection it holds (members, origins, type arguments, and the properties and signatures of spelled-out object types, 4 levels deep) groups its members by everything but their type arguments and mappers and sorts each group by text; the generator's playground reads union members through `canonicalUnionMembers`. A new file's types reach an existing page only through a file of its closure (an import resolution or content change there) or through a global file (`env` holds every declaration and global-scope file's content). A patched program keeps the cold file order (pinned roots), and a fragment that adds a file outside the program pins the existing roots and appends it (`semantic/fragments.ts`, `withPinnedRoots`). The order differs from the legacy engine's in some API pages (the members are the same); changing the option changes output. The generator's playground option lists never use the checker's order: `helpers/playground/written-union-order.ts` (used by `semantic/angular.ts` only; the legacy engine keeps its checker order) lists an input's union members in the order its written type node names them, through unions, parentheses, non-generic type aliases and enums; members the syntax does not name keep the checker's positions.
- **Records.** The artifact carries only the digest. `R` and the derived identities stay in the retained program (`RetainedProgram.closures`, keyed by digest), and the refresher recomputes the digest from them over the current program. A digest without a record holds only while the program equals the previous candidate's (`closureBase`: the aggregate's `semantic` digest). Without records, a mutated program therefore re-renders every closure after the first program edit. A runtime that carries no records (the startup generation's one-shot runtime, a fresh, recycled or primed long-lived one) takes them from the **closure store** (`compiler/closure-store.ts`): every development generation that writes the cache also writes, beside it (`<hash(projectId)>.semantic-closures.json`, best effort, atomically replaced, stale temporary files of an interrupted save swept; skipped when the file still holds the bytes this process last read or wrote for the same digests), the records of every closure its candidate holds, and `synchronize` is followed by `seedClosures`, which loads them only for a generation with no carried records. A stored record is checked every time it is used, like a carried one: the digest covers `R` and the derived identities, so a record recomputes to its dependency's digest only when it is that digest's record and the closure holds; a missing, stale, corrupt or foreign store only makes units render again, and one written by another compiler, toolchain, `GENERATOR_SCHEMA_VERSION` or configuration digest is not read. While the program equals the previous candidate's, a stored record is carried without being recomputed (the closure holds anyway), so a restored start pays no digest work. The store is kept only by development generations with incremental reuse, the cache, closures and the targeted rebuild on (`NGDOC_TARGETED_REBUILD=0` neither reads nor writes it); a project with `cache: false` keeps none, and its first program edit after a start still rebuilds every semantic unit. A start restored from a cache without a usable store writes an almost empty one (its reused IRs carry no records); its first program edit then rebuilds the semantic units once, and the store holds their records from then on.
- **Fallbacks to the global reference:** recording off or unavailable, an incomplete footprint (a language-service search outside a derived-class query, a recording failure), a query that added a source file to the program, and a failed query. In scoped generations the refresher also refreshes such a reference against the current program (`semanticReference`), since no descriptor carries it.
- **`whyRebuilt`**: a rebuilt owner that the index cannot explain reports `semantic` with the first closure key whose digest changed.

## Lifecycle and processes

- **`BuildSession`.**
  - `buildOnce({ mode })` defaults to production.
  - `watch(source, onEvent)` returns `Promise<WatchHandle>` (`{ initial, dispose }`) and emits the events `started | result | diagnostic | unchanged | disposed`.
  - `reconcileInputs(paths)` re-observes paths a host has only just begun watching against what the newest settled generation observed. A difference is admitted as an ordinary watched change; when nothing differs no generation runs.
  - `rescan()` makes the watch re-observe every committed input before its next generation, as after a lossy-watcher error. Differences become `filesystem` changes, and the compiler keeps its retained program only if the program's own sweep holds; with none it is a `reconcile` generation, which discards the program. Either way the commit is the full one. The Vite host calls it when the changes it rejected during a generation overflowed their bound.
  - Both resolve once their work is scheduled and never wait for a generation; its result arrives as a watch event. Without an active watch they do nothing.
  - `dispose()` tears everything down.
  - One session owns exactly one compiler and one committer. A superseded generation whose commit already landed is adopted and reported as `superseded: true`.
- **Production.** Always a fresh one-shot worker. It enumerates and validates every page, including pages nobody opened in development, and never retains state. The Vite production pipeline (`buildNgDocViteApplication`) generates once: its browser build records the published result in a handoff that both builds' configurations carry (`NgDocGenerationHandoff`, a plugin's `api.ngDocGeneration`), and its server build, whose NgDoc plugin has the same generator options, publishes that result again (the lease, the generated assets) instead of generating, but only while the output root still publishes the recorded manifest (`artifacts` `publishesManifest`: another writer may commit while the lease is free between the builds); otherwise, and with `NGDOC_VITE_BUILD_HANDOFF=0`, it generates.
- **Development watch.**
  - By default there is one long-lived compiler worker per watch session, and it creates a fresh `CompilationService` per generation. It also serves the development `buildOnce` that precedes the first watch (see the first edit after a start, above).
  - `worker/entry.ts` isolates host state between generations (env, cwd, listeners, user CommonJS modules).
  - Abort is cooperative first, then SIGKILL after a grace period.
  - An idle runtime is recycled after a generation count or RSS limit (`PersistentWorkerOptions`).
  - A crashed runtime is recreated.
  - On POSIX each runtime (one-shot and long-lived) leads its own process group, and it counts as ended only once that group is empty: what it started (the compiler's esbuild service, which otherwise exits only after it reads the end of its stdin) is killed with it. Every runtime is tracked until then, so `watching(false)` and `dispose()` resolve only when no runtime, retiring or crashed ones included, and none of their children are left. Windows has no process groups; there only the runtime is signalled.
  - The host itself keeps no child either, exited ones included: a child nobody reaps stays a zombie in the host's process group until the host exits, where a supervisor that waits for the group to empty finds it. NgDoc's watcher (`session/parcel-event-source.ts`) therefore names inotify on Linux (`nativeWatcherBackend`) unless the caller names a backend: @parcel/watcher's default there probes for Watchman through `popen` and, without Watchman, never reaps the probe's shell. Tests: `bootstrap/testing/lifecycle-processes.vitest.ts` (a production build, a watch with an edit and dispose leave no runtime, runtime child or child of the host) and the packed consumer's lifecycle script, which checks its own process group after dispose.
- **Vite dev server close** (`vite/bounded-close.ts`). The plugin replaces `server.close()`. It always waits until NgDoc's worker, SSR renderer, watchers and output lease are released, then gives Vite's own close and the rest of the disposal 5 s. On timeout it logs one `NGDOC_VITE_CLOSE_TIMEOUT` warning and resolves; failures within the bound are rethrown. Vite 7's dependency optimizer never settled requests for dependencies whose first optimization a close cancelled, so `server.close()` could hang; Vite 8 settles them, and the bound stays as a safety net for any request or hook that never settles.
- **Component updates** (`vite/component-updates.ts`). Angular's HMR code loads a component's metadata update (`@ng/component?c=<file>@<class>&t=<timestamp>`) on each `angular:component-update` event and once more whenever its module is evaluated. Analog's endpoint answers that load-time request with the file's last update (one per file, the last component's) as soon as Vite has ever invalidated the module, and its SSR path always does. Vite invalidates every module when the dependency optimizer reloads the page, so a file with two components then got the wrong metadata on every load until a restart (`Cannot read properties of undefined (reading 'MatButton')`). The plugin's `@ng-doc/vite:component-updates`, ahead of Analog, records the update events sent on the HMR channels and lets a request through only when its `c` and `t` are those of a sent event; any other request, client or SSR, gets an empty module. Tests: `vite/testing/component-updates.vitest.ts`.
- **Development first paint** (`vite/dev-styles.ts`, used by `createNgDocApplicationPlugin`). The development server renders in the browser only, so its index page carries what a server-rendered page would: each global style sheet inlined as `<style data-vite-dev-id>` with the id Vite's client adopts (read from the style module the page imports anyway; a `?direct` request would add a second module that every edit hot-updates, and the client would reload), and an inline gate that hides the body during the initial load only, until every component style sheet (`?ngcomp`, Analog live reload) added by then has loaded. The initial load ends after a quiet period, at the first input or at a time limit; later components (dialogs, the search palette) are never hidden. A global sheet, and a Sass file only global sheets use, reaches only the virtual browser entry, which Analog cannot recompile, so `angular-composition.ts` (`globalStyleSheet`) leaves their hot updates to Vite instead of poisoning the compiler. Tests: `vite/testing/dev-styles.vitest.ts`, `application.vitest.ts`, `angular-composition.vitest.ts`.
- **Host update coordination** (`vite/host-updates.ts`). An edit settles, and the browser reloads, only after Vite reported a hot update for every generated module its commit created, rewrote or deleted, and after the compiler pass of a rewritten generated TypeScript module witnessed each created or deleted TypeScript source of the generation. Vite watches its root recursively but a file outside it only once served, so an output root outside the Vite root (the site's `apps/ng-doc/src` root) is added to the watcher before the watch starts, and startup waits until every published directory is listed (`vite/output-watch.ts`); otherwise new files (a page tab, a page) and pages nobody opened never report and the edit fails with `NGDOC_VITE_HOST_TIMEOUT`. An output root inside the Vite root is in its recursive watch, but the initial commit runs while chokidar still scans that root, and its `fs.watch` backend (Linux) reads a directory before it attaches the directory's watch: a file published in between is never listed or reported. So each published directory the watcher does not yet list in full is added again (read once more, its files taken as initial), and startup waits for the same listing. A generation that rewrites no generated TypeScript module (a category without pages, a component no page imports yet) takes no such pass, so its sources are released with its result. Under load FSEvents may deliver a file's creation and its write apart, so the watcher reports a created output as changed, after its creation or (for a path it still knew) instead of it: that report is the creation (it satisfies the expected shape and binds to its generation), so the generation neither waits for a creation report that never comes nor lets the update compile outside it. A later report of an output whose generation completed it, while the file is still the one that generation wrote, is a repeat (`HostToken.repeat`): it is announced with that generation (Vite adds no reload of its own) and obliges nothing. Tests: `vite/testing/page-tabs.vitest.ts` (real Vite/Analog, output outside the root: tabs added, renamed and removed, pages, categories and demos added and removed, each settling byte-equal to a cold build) and `vite/testing/structural-updates.vitest.ts`.
- **Bursts of file events** (`vite/host-updates.ts`). Thousands of file events at once (a script churning files in the docs folder, a checkout) flood Vite's hot-update pipeline: host updates wait past `HOST_COMPLETION_TIMEOUT_MS` (30 s), a hook that timed out throws and leaves its generation's obligation open (nothing reports that output again, so no reload was ever sent), a starved compiler worker misses its deadline, and chokidar may lose events without a signal. The coordinator tracks a burst: `HOST_BURST_EVENTS` hot updates of files outside the output root (counted only after `seed`, so NgDoc's own writes never count) within `HOST_BURST_WINDOW_MS`, or any host update timeout, opens one; `HOST_BURST_QUIET_MS` without either ends it. Only the burst's first `NGDOC_VITE_HOST_TIMEOUT` is reported (through `fail`, as before); the rest are summed up in one warning when it ends. Then it takes one more pass (`HostUpdateRecovery`, wired by the lifecycle): every open output expectation whose file still holds its generation's bytes is replayed as a Vite watcher event (`server.watcher.emit`, path order; the newest generation's expectation per path), and once no generation is in flight the session rescans every recorded input. A replayed report is matched like any other, a duplicate is a repeat, so an edit still reloads once. Tests: `vite/testing/host-bursts.vitest.ts` (a timed-out hook's outputs replayed and one reload; 500 timeouts logged as one error and one summary; the burst threshold, quiet period and in-flight deferral; NgDoc's own writes; a failing host; an edit whose generation failed with `WORKER_COMPILE_TIMEOUT` under a burst published by the rescan, through the real lifecycle, session and committer).
- **One Angular pass per generation** (`vite/angular-composition.ts`, `NGDOC_ANGULAR_SHARED_PASS`). Every pass of the patched Analog compiler analyzes and type-checks the whole program, whatever changed, and Analog compiles one file per hot update. So a page title edit, which rewrites the page shell, `routes.ts` and `context.ts` in place, used to cost one full pass per module after the commit. The first generated TypeScript update of a generation (after `ticket.ready`) passes the other TypeScript outputs that generation created or changed in place and whose updates have not completed (`HostUpdateCoordinator.compilerCompanions`) to its pass as `ngDocCompanionFiles`; the `generation-companion-pass` change of `tools/compatibility/analog-2.8.0-resources.json` adds them to the pass's modified files and exposes the pass as `ngDocCompanionPass`. The companions' physical states are read before the pass starts (at most 16 reads at once) and handed to Analog as forward-slash ids (`analogFileId`, the keys of Analog's per-file maps); after the pass succeeds, the states of its own file and its companions are kept until a pass fails, and an update of any of them acknowledges without a pass (never as a compiler pass) only while its current version and digest equal that state: a watcher under load may report one write twice, or a created output as changed. A successful shared pass checked the whole program with its companions read afresh, so it repairs every diagnostic recorded before it started (`diagnosticMark`, `acknowledge(…, recoverBefore)`), including those of updates numbered after it; otherwise a covered update could be skipped while an earlier diagnostic holds the reload. A compiler that does not expose the pass, a failed pass (it drops every recorded state, so no update is skipped after a later failure) and a companion rewritten since take ordinary passes. Tests: `vite/testing/shared-pass.vitest.ts` (including repeated reports and created outputs reported as changed) and the native differential in `vite/testing/startup-native.vitest.ts` (one pass on, one per report off, the same served modules).
- **The structural pass** (`vite/angular-composition.ts`, `NGDOC_ANGULAR_STRUCTURAL_PASS`). Analog compiles the whole program on every add and unlink event of a TypeScript file (`createFsWatcherCacheInvalidator`, 100 ms debounce), on the host's main thread. A commit that adds, moves or deletes pages creates and deletes generated modules and rewrites `routes.ts` (or a page shell) in the same commit, so that event pass compiled the program before the importer changed, and the generation's shared pass compiled it again; the new description module's own add event added one more pass, which also held back the session's commit while it ran. The `generation-claimed-filesystem-*` changes of `tools/compatibility/analog-2.8.0-resources.json` expose `api.ngDocHost`: `claimFilesystemChange(file)` (set by the composition) may claim an add or unlink event, which then still invalidates the include and tsconfig caches at once but starts no pass; every claimed file joins the next pass (`modifiedFiles`, its cached bytes dropped, not emitted until a transform asks); `passes` counts the passes (for tests). The host claims a generated output (`HostUpdateCoordinator.generated`: below the published output root) and a description module (`ng-doc.{page,category,api}.ts`) the generator watches (`ViteAdapterLifecycle.hostClaimsFilesystemChange`), unless the newest committed generation read that module (a `content` dependency of its snapshot) and it exists when the event arrives. A new description module is imported by no generated module before its generation commits, and a deleted one has nothing left to compile; an existing one is in the program (its page shell imports it), and an add event that replaced it (an atomic save, a checkout) may change it without changing any generated module, so it compiles in its own pass as before. A claimed file whose generation fails or rewrites no generated module waits for the next pass. Every other add or unlink compiles as before. Tests: `vite/testing/structural-pass.vitest.ts`, the native differential in `vite/testing/startup-native.vitest.ts` (a tab route edit: one pass on, at least two off, the same served modules; a page added, a failing page, a category without pages, an existing description module replaced by an add-only event and a page deleted, with their pass counts and served bytes) and the structural corpus of `vite/testing/page-tabs-structural.vitest.ts` (a page added, renamed, retitled and deleted and a category added, each update equal to a cold build, with the switch on and off).
- **Progress** (`session/progress.ts`, `progress/`). Advisory only: results are byte-identical with and without it, and it never writes into generated output.
  - `SessionOptions.onProgress` receives every generation's events, `buildOnce` included: `progress-started` (before a rescan's reconcile), the session's own `commit` phase (a total only for a full commit), then exactly one `progress-settled` (`success`, `superseded` for a commit adopted after supersession, `failure`, `cancelled`) with pages, rebuilt pages, errors, warnings, files written, removed and unchanged, and up to three routes of an edit's pages. Updates are forwarded only while the generation is current. The input check after a watch starts and the warm-up are `progress-activity` events; a warm-up stopped by work ends (`stopped`) before that work starts. The warm-up is shown only in `verbose` output, except a failed one, which always prints. A failing consumer is reported once as the `SESSION_PROGRESS_FAILED` warning and never stops anything.
  - Triggers: a `buildOnce` is `build`, a rescan or reconcile generation `rescan`, other watch generations `watch`.
  - Compilation phases reach the session through `CompilationContext.progress` (`contracts.ts`: `CompilationPhase`, `CompilationProgressUpdate`), a sink attached non-enumerable like `retention`; the session stamps each update with its own clock and forwards it only while the generation is current. Without a consumer there is no sink and the compiler does no progress work. The compiler (`compiler/progress.ts`) marks `discovery`, `restore` (the fast start's check), `semantic`, `plan`, `describe`, `render`, `keywords`, `link`, `assemble`, `aggregate` and `persist` at their call sites in `compiler/index.ts`, with totals for describe (entries), render and link (units) and one advance per unit (render also counts units whose content was reused). A fast start ends its `restore` phase with `pass: 'restored'`, which the result line reports (`OK restored …`) and after which the worker relay starts the `transfer`; a start whose check failed reports `full` with `fast start: <reason>`. A generation that tries the targeted path reports `pass: 'targeted'`; its fall back to the full path reports `full` with the reason on the next phase start, and the phases may start again once (the session keeps the times of the phases before the restart point). A generation the targeted rebuild classified as full before compiling reports `full` with that reason from its first update; one it never considers (switched off, buildOnce, production) reports no pass. Preparation repeated without the pinned keyword loader results before admission is not reported, and the `verify` oracle compile reports nothing. The worker (`worker/protocol.ts`) asks a runtime for progress with `progress: true` on the compile message (never for a warm-up, nor for a delta retry once the first attempt reported a compiler update); the runtime sends `{ type: 'progress', id, update }` JSON messages before its reply, with `advance` coalesced to one per 100 ms. The host takes them out of the reply stream like `idle`, drops a malformed (including `completed` above `total` or `reused` above `completed`), foreign or pre-ready one silently, relays nothing after the job's abort, and adds `boot` (a runtime starting for the job) and `transfer` (from the compiler's `persist` end to the result the caller receives). With compiler phases the output shows the four steps (preparing, rendering, linking, writing) with counts and a percentage.
  - Hosts create one `createHostProgress` per session, pass its `sink` as `onProgress`, call `interrupt()` before printing their own lines (it clears the live line), `release(generation, failed?)` once they have printed a result (its diagnostics; `failed` when they could not publish a committed result, which turns its line into the failure line), and `setForeign` once another writer shares the terminal. A writer that throws stops progress with one `[SESSION_PROGRESS_FAILED]` warning through the host's warning channel. CLI: progress on stderr, result lines on stdout, `--progress <mode>` or `--progress=<mode>`; the summary replaces `Generated … at …` (kept in `verbose`), `--json` is unchanged unless the setting is `json`, and a host spawned by `dev` gets result lines only. Vite plugin: the `progress` option, the initial result's diagnostics logged before its summary, lines through the Vite logger (never with `clear`), the live line on stderr until the dev server is configured, then timestamped lines (`[vite] NgDoc: updated …`). A line identical to NgDoc's previous one gets `(N in a row)`, because the Vite logger clears the screen for a repeated message. `logLevel` `warn`/`error`/`silent` turns progress off; a non-`auto` setting still turns it on, and its lines then go straight to stderr, since the logger would drop them.
  - Settings: CLI flag > `NGDOC_PROGRESS` (`auto`, `live`, `plain`, `verbose`, `summary`, `json`, `off`) > the Vite plugin option > host quiet settings (Vite `logLevel`) > `auto`. An explicit `auto` means "decide for me", so host quiet settings still apply to it. CI, Nx shared output, non-TTY streams and `TERM=dumb` get plain lines at a bounded cadence; `NGDOC_PROGRESS_SECTIONS=1` adds GitHub/GitLab groups. A single Nx task on a TTY keeps the live line (cut to 55 columns, `NX_TASK_COLUMNS - 1`; no bar). An `nx:run-commands` command always runs in an Nx PTY, and nothing in its environment says whether Nx streams or collects its output, so under `run-many` without the TUI its live frames are printed when it ends (documented; `NGDOC_PROGRESS=plain` avoids it).
  - The live line is cleared at `exit` and on SIGINT, SIGTERM and SIGHUP (`progress/live.ts` `processExitHook`): Vite has no handler of its own, so Node would end without `exit` listeners. The listener is prepended, so it clears before a host's handler prints, and the renderer then never draws again, even if the host lives on. Next to a host's listener it changes nothing else. When it is the only listener, it gives Node's default ending back: it resets stdin raw mode (the rest of Node's own stdio reset on a fatal signal is not reproduced), removes itself and raises the signal again; on Windows, or when `kill` throws, it exits with `128 + signal number`.
- **Delta transport.**
  - A persistent runtime keeps the committed snapshot of its base, so a request carries only its changes and base revision. The result returns a `SnapshotDelta`, which the session applies to its own snapshot (deep-frozen, shared).
  - A candidate becomes the runtime's base only after the session acknowledges its commit (`acknowledge` → `committed | discarded`).
  - Any disagreement falls back to a full resync.
- **Retained program.** A development watch generation keeps its TypeScript program for the next generation of the same runtime, keyed by compiler options. It is reused only when the next request's base is exactly the committed candidate it was built for. A consumed or mutated program is never restored. The compiler talks to it through the contract's `SemanticProgramRetention` port: `synchronize` takes `retention.previous` off the request unless it keeps the program, and `programSynchronization()` reports `reused | patched | patched-failed | full`.
- **Incremental program** (`semantic/program-retention.ts`, `NGDOC_INCREMENTAL_PROGRAM`). When the only changes a retained program observed are the contents of its own files, `synchronize` patches them into the Project instead of building a new one (at most 50 files):
  - **Eligibility.** Each file is a TypeScript module before and after the edit: no declaration, JSON, library or script file, no `declare global`, ambient `declare module` or `export as namespace`, and the same import, reference, type-reference and lib directives (`ts.preProcessFile`) and pragmas (`@jsxImportSource` adds an implicit import). Everything else the program observed must hold exactly as for a reuse; a change event of a program file that still exists is explained by its content. Anything else is a FULL synchronization.
  - **Pinned roots.** ts-morph re-creates a changed program from every file in its cache (the resolved dependencies included), which changes the root set and the file order. The patch passes the root names of the FULL synchronization (`ProgramMirror.roots`), so the patched program has the cold file set and order, and TypeScript reuses its structure.
  - **Applying the text.** The new text replaces the file's compiler node through ts-morph's compiler factory, parsed as ts-morph parses a loaded file (byte order mark stripped, line endings kept). ts-morph's text manipulation (`replaceWithText`) must not be used: its code writer normalizes CRLF.
  - **Post-invariants.** The same root names, files and order; each re-tracked file resolves exactly what it did (`ProgramObservations.retrack`, which also gives a program file's global read, such as an entry file's, the new digest, as a cold synchronization does); then the cold syntax check. Anything else is a FULL synchronization with the program consumed.
  - **Documentation caches.** TypeScript caches a symbol's documentation (inherited documentation included) on the symbol, and a patched program reuses the symbols of unchanged files. `semantic/documentation-cache.ts` drops that cache when another checker asks, and the recorder captures documentation reads per checker.
  - **The slot.** The Project is patched in place, so a `patched` program is offered for its candidate only and is never restored for the taken base (the slot is told `invalidated: patched`); if that candidate is not committed, the next generation builds anew. A `patched-failed` synchronization (a syntax error after the patch) reports the cold diagnostic and observations and hands back the taken program object, which the slot restores as it is; its `ProgramMirror.appliedSinceBase` (written before the Project changes) keeps the applied paths, so the next synchronization of that Project re-checks them and never reuses it as it is (with the switch off, it rebuilds).
  - **Root and file set changes** (`restructureProgram`, the structural class): entries added, removed or moved, an API scope or tsconfig glob that gained or lost a file, a deleted program file, and an edit whose imports, references or pragmas changed. `assessRestructure` requires the program configuration (the root membership's reads other than entry modules), every program file that stays and was not edited (its whole observation segment, so its resolution is unchanged), the formatter probes and the private observations (types directives, missing directories, symlinks, type root listings) to hold. The patch observes the root membership again with `programMembers` (the FULL synchronization's own function), takes the root names ts-morph gives a FULL synchronization (its glob of the members; the kept roots must keep their relative order, and the members' parent-most folders, which ts-morph marks as in the project, must be the base's), drops deleted files and every cached file the new program does not contain, adds the new roots and resolves their dependencies as a FULL synchronization does, and lets TypeScript re-create the program (the roots changed, so its structure is not reused): a file that keeps its observations takes the base program's module resolutions (`reusingResolutions`; they cannot differ), every other file is resolved against the tree. New, edited and deleted files must be TypeScript modules; a syntax error is refused (the Project is not kept). The observations are rebuilt in the cold log's order (`ProgramObservations.restructure`: the new membership, kept segments and newly tracked files in program order, the tail), and so are the stamps, missing directories, symlinks and glob listings. The closures' global observation digest is unchanged by construction (the membership's non-program reads hold). At most 50 files change at once.
  - **Differentials.** `semantic/testing/program-patch.vitest.ts` (patched and restructured equal a cold synchronization, every refusal, the syntax-error chain, `verify`) and the patched arms of `compiler/retained-program.vitest.ts` (byte-identical to the reference chain and cold compiles, with the switch on and off).

Kill switches:

- **Defaults:** every feature is on by default.
- **Turning one off:** an environment value of `0|false|off|no` (case-insensitive) turns it off. `1|true|on|yes` or an empty value leaves the option in charge.
- **Unrecognised values:** the bootstrap switches warn once per process on an unrecognised value.
- **One registry:** every switch is registered in `kernel/flags.ts` (`FLAGS`, `readFlag`, `flagOff`), and parsed by `readFlag`, so host and compiler runtime read a switch the same way. The one exception is `worker/index.ts`, which keeps its own `NGDOC_INCREMENTAL_SKIP` check because its only runtime import is its sibling `protocol.js`. Register a new switch there first. `progress/settings.ts` `ENGINE_SWITCHES` lists only the switches that do something, and a test keeps it consistent with the registry.
- **Option equivalents:** `GeneratorBootstrapOptions.worker.persistent` (`false`, `{ prime: false }`, `{ delta: false | 'verify' }`), `CompilationOptions.incrementalReuse`, `CompilationOptions.targetedRebuild` (`false | 'verify'`), `CompilationOptions.scopedSemantic` (`false | 'verify'`), `CompilationOptions.incrementalProgram` (`false | 'verify'`) and `CompilationOptions.fastStart` (`false | 'verify'`). `NGDOC_SHAPE_CLOSURE` has only `SemanticServiceOptions.shapeClosure`, `NGDOC_SEMANTIC_RECORDER` only `SemanticServiceOptions.recorder`, and `NGDOC_TRACKED_PROGRAM_REUSE` only `SemanticServiceOptions.trackedProgramReuse`. `CompilationOptions.highlightCache` (`false | 'verify'`) is `NGDOC_HIGHLIGHT_CACHE`'s, `CompilationOptions.formatCache` (`false | 'verify'`) `NGDOC_FORMAT_CACHE`'s, `CompilationOptions.parallelRender` (`false | 'verify'`) `NGDOC_PARALLEL_RENDER`'s (`renderThreads` sets the pool size), and `CompilationOptions.usedGrammars` (`false`) `NGDOC_USED_GRAMMARS`'s. `NGDOC_PARALLEL_WRITES` is resolved in bootstrap into `OutputCommitterOptions.parallelWrites: false`, as `NGDOC_TARGETED_REBUILD` is into `delta: false`.

## Invariants (do not break these)

1. **Determinism.** The same inputs produce byte-identical outputs, manifests, search records, keywords and diagnostics, in the same order. Sort explicitly, and never depend on iteration order of filesystem listings, `Promise.all` completion or `Map` insertion from concurrent work.
2. **Incremental equals full.** Every incremental result (reuse, retained program, delta transport, persistent worker) must equal the reference path (`incrementalReuse: false`) exactly. Every published output must equal a cold build of the same tree. That includes union member order (`stableTypeOrdering`, see scoped semantic invalidation). Known limitation: two members that tie on every key including their symbol's declaration position (`compareSymbols` ends with the symbol id), and ties nested deeper than the canonical-order walk goes (`semantic/type-text.ts`), keep the checker's creation order; a shared-checker scan of `apps/ng-doc` in two checker histories found none. When unsure whether reuse is valid, recompute. A missing, stale or corrupt memo or cache entry may only disable reuse; it can never change output.
3. **Exact dependencies.** A dependency records the digest of exactly the bytes that were compiled. Reads, glob memberships and existence checks are all dependencies, because absence is not an empty file. Anything a phase reads must be recorded, or watch mode will miss the edit. Every recorded path, watch input and DTO path is resolved and uses forward slashes on every OS (`D:/a/docs/page.md` on Windows; `kernel/paths.ts` `hostPath`); `session/watch-inputs.ts` rejects a backslash, so a path built with `node:path`, including one returned by a shared helper in `libs/builder/helpers` (`getComponentSourceFiles`), goes through `hostPath` before it is recorded. Tests compute expected paths the same way, never with a bare `path.join`.
4. **Fingerprints and digests.** A cache entry is keyed by an `ArtifactFingerprint`: schema version, compiler version, toolchain digest, configuration digest, input digest and keyword digest. Artifact revisions are content hashes. If a new input can change output, it must flow into a fingerprint or a dependency.
   - **One digest domain** (`kernel/canonical.ts`). Every persisted or compared digest is `digestOf(value)` (one `sha256` over `canonicalJson`: JSON semantics, object keys in code-unit order) or a file's content digest, `bytesDigest(bytes)`; a reader that holds only decoded text uses `contentDigest(text)`, the same function over its UTF-8 encoding. Never order what a digest or key covers with `localeCompare` (it depends on ICU and the locale, and ignores `\0`); use `compareCodeUnits`. An order that reaches output and must stay English uses `compareText` (`helpers/text-order.ts`, a fixed collator), never the process locale. Dependency identities come from `dependencyIdentity`. Record file reads through `kernel/observations.ts`, so a path read by several phases has one digest: TypeScript drops a leading byte order mark, so the semantic service digests such a program file from its raw read (`OwnedRoots.contentDigest`).
   - **Output identities keep their formulas.** Content module ids and revisions, keyword digests, declaration ids and output ids are written into generated files, so they keep their fixed `JSON.stringify` formulas (hashed with `sha256Hex`); canonicalizing them would change generated files.
   - **Changing a digest formula** changes values, not shapes: bump `dependencyRepresentation` in `compiler/common.ts` `inputDigest`, so every cache entry written with the old formulas misses. A shape change still bumps `GENERATOR_SCHEMA_VERSION` (invariant 10).
5. **Commit protocol** (`TransactionalOutputCommitter`):

   1. One commit at a time.
   2. The generation guard is re-checked live (`stale` results are not errors).
   3. The on-disk manifest (`.ng-doc-output-manifest.json`) must equal the expected previous manifest.
   4. Paths are validated for ownership and collisions.
   5. Outputs are staged under `.ng-doc-stage-*`, backed up and published by rename. A replaced file (an output or the manifest) is backed up as a copy (a copy-on-write clone where the file system has one) and the publish rename replaces it in one step, so it is never missing: moved away first, a reader between the two renames found no file, and chokidar's `fs.watch` backend (Linux) reported the rewrite as a deletion and a creation, which the Vite host never matched to the expected change. Not a hard link: inotify reports the link count change (`IN_ATTRIB`) as a change of the old bytes, and chokidar drops the publish's own change within its 50 ms throttle, so the host timed out. Where the copy fails with any file system error (a full volume, a file held open on Windows, mounts that answer `ENOTSUP`, `ENOSYS` and others), the file is moved away as before. The rollback leaves a file the commit had not replaced yet in place (the copy records its inode) and restores the backup's bytes otherwise. A new directory (every output below it new, none of them a late role: routes, context, search, API list) is published whole, with one rename of its staged copy: the same backend reads a new directory before it watches it, so an output renamed into it in between was never reported, and the host timed out (`NGDOC_VITE_HOST_TIMEOUT`). On win32 each rename (and the rollback's) is retried in place while it fails with EPERM, EBUSY or EACCES (`retryingRename`, about 3.5 s at most), so the order holds. **Parallel writes** (`NGDOC_PARALLEL_WRITES`, on by default): the staging writes and their stage directories, then the backup copies of the outputs published one by one, run concurrently (`runBounded`, at most `WRITE_CONCURRENCY` at a time) before the first publish rename; the renames, their hooks and the stats of delta commits keep the sequential order. A failure, a stale guard or an abort starts no further operation and waits for those in flight before the rollback, and the first failure in plan order is reported. A backup taken early leaves its output untouched and gets a rollback record only when its output's turn comes, so a failure before then leaves that very file in place; where its copy fails, the output is moved away right before its own publish rename, as without parallel writes.
   6. The manifest is written **last**.
   7. Any failure rolls back.

   An unchanged output is re-read and compared unless its verified lstat identity (device, inode, size, mtime, ctime) still matches; these read-only checks (`checkOutputs`: the verified identity, `assertSafeTarget`, the byte comparison) run concurrently and their outcomes are applied in plan order, so staging and the first failure are those of the sequential loop. An unchanged output is never rewritten. Never write into the output root outside the committer.

   **Delta commit** (on unless `NGDOC_TARGETED_REBUILD` turns it off). A watch development commit that passes `CommitRequest.base` (the committed snapshot and manifest of one acknowledgement) plans only the artifacts whose revision or outputs changed. Every step above still applies to them, and the result must be byte-identical to the full commit. It may be used only when all of these hold:

   - the base names the manifest this committer published in its **previous** call, which ended `committed`;
   - that manifest's lstat stamp, taken right after its rename, is unchanged;
   - the configuration is unchanged.

   Anything else runs the full commit, which reports every failure. Unchanged outputs are not re-verified by a delta commit: a full commit repairs external edits of them. The session asks for the full commit outside a watch, for reconciling generations, when the compiler reports `output-missing`, and for every generation its compiler does not report as targeted (`targetedResult`). The compiler must keep that existence check for every previously published output. A published file's stat is recorded as verified only while it is provably the file the commit wrote: the same inode, size, mtime and post-rename ctime, finer than whole seconds, and outside the racy window.

6. **Owned roots.** Output and cache roots must not overlap documented sources or the TS program, and must not be inside each other. Compare paths through `realpath`.
7. **Worker boundary.** Only JSON values cross it (the compiler runtime's process and its render threads alike); functions, class instances and non-finite numbers throw. No user-module state may leak between generations.
8. **Diagnostics, not exceptions.** Services return `ServiceResult`/`Diagnostic` with a stable code (prefix by module: `DISCOVERY_`, `SEMANTIC_`, `CONTENT_`, `COMPILATION_`, `GRAPH_`, `OUTPUT_`, `ARTIFACT_CACHE_`, `SESSION_`, `WORKER_`, `BOOTSTRAP_`) and a `stage`. Hosts throw `Error('[NGDOC_VITE_…] …')`-style prefixed errors. Codes are public behaviour: don't rename them casually, and add new ones with a test.
9. **Production is complete.** Production always renders, validates and emits every page.
10. **Contracts evolve additively.** New fields are optional. A breaking change to a persisted shape bumps `GENERATOR_SCHEMA_VERSION` (the fingerprint, descriptors and IR: a cache entry of another version is a miss, and a cache index of another version is rebuilt with one `COMPILATION_CACHE_FORMAT` warning), and `contracts.spec.ts` must be updated. The output manifest is read across versions and carries `OUTPUT_SCHEMA_VERSION` instead.
11. **Non-physical dependencies.** `semantic-closure` (`scopeId`, `key`, `digest`) and `evaluated` (`entryId`, `digest`) name no path: they are never watch inputs, physical observations, graph path edges or unit-index paths. Their identity (`nonPhysicalIdentity`: one closure per scope and key, one evaluated digest per entry) is shared by every dependency key and collapse. The cache, watch-input and worker boundaries accept them with their exact shapes. A kind without a refresh source is reported as changed by the refresher (`UNREFRESHED_DIGEST`), so a unit recording one is always recomputed.
    - `evaluated` is produced by discovery: the canonical digest of an entry's evaluated default export and its guide values (repeated references by path; functions by source text, and a value that holds one is also keyed by the whole bundle's code, since a call can read state any module mutates; a value that cannot be canonicalized without running user code, such as an accessor, a proxy or a class instance, leaves the entry unattested, and its digest is then the whole bundle's). Discovery records it in the entry's dependencies and in every template render of the entry. The refresher recomputes it from the generation's fresh discovery snapshot (`evaluatedDigests`, passed as `DependencyRefresherOptions.evaluated`), never from disk. A rebuilt unit whose only change is an evaluated value reports the reason `evaluated`.
    - `semantic-closure` is produced by the semantic service in development generations (scoped semantic invalidation, below). The refresher recomputes it through `DependencyRefresherOptions.semanticClosure`. The targeted path replays a unit without refreshing its closures only while the program equals the base's (`closuresHold()`); otherwise its admission refreshes every replayed unit's closures (and global references) and makes the entry of each unit whose closure changed a candidate, and a generation without closures (`NGDOC_SCOPED_SEMANTIC=0`) takes no program edit.
    - Every producer must make each unit whose recorded non-physical dependency changed a targeted candidate (or fall back to FULL): the targeted path replays non-candidate units, while the full path recomputes them. An API declaration unit is a candidate on its own; the enumeration's own record (the API entry unit's first describe contribution) is compared with a fresh enumeration whenever the program is not the base's. A new producer's change of the dependency format bumps `GENERATOR_SCHEMA_VERSION`.

## Development content

- Generated content is always committed to disk and loaded like normal sources, in development and production. The Vite/Analog host with these physical files is the only optimized development host.
- The former virtual content mode (`developmentContent: 'virtual'`: Vite virtual modules rendered on demand) was removed from the hosts. `createGeneratorBuildSession` rejects it with `NGDOC_DEVELOPMENT_CONTENT_REMOVED`; `'file'` is still accepted and is the same as omitting the option.
- Its lazy transport is gone from the core as well: the compiler renders and links every descriptor in every generation, `CompilationRequest` carries only the watch origin (`filesystem` or `reconcile`), and `CompilationResult` has no demand fields or content failure scope.
- The persisted shapes no longer carry that mode's fields: `PageArtifact` has no `deferredContentIds` and `ArtifactSnapshot` no `contentIndex` (`GENERATOR_SCHEMA_VERSION` 3; a version 2 cache is a miss and is rebuilt). Every descriptor of a page artifact has its linked content; the cache and committer validators reject an artifact or snapshot that carries either field, and the assembler reports a descriptor without content as `OUTPUT_DESCRIPTOR_FILE_DEFERRED`. The compiler memo's link facts no longer carry a completeness mode (memo file version 2).
- The runtime counterpart is gone too: `@ng-doc/app` has no search index source (`NG_DOC_SEARCH_INDEX_SOURCE`, `NgDocSearchIndexService`) and `@ng-doc/core` no `NgDocSearchIndexModule`/`NgDocSearchIndexSource`; `NgDocDefaultSearchEngine` always loads `assets/ng-doc/indexes.json`.

## Build and shipping

- **What `builder:build` runs:** `build-schema.js`, then `tools/scripts/build-generator.mjs`.
- **How the bundle is built:** the script snapshots every hashed input and esbuilds the `GENERATOR_ENTRY_POINTS` to ESM (`node24`). The package itself is CommonJS.
- **Provenance:** it writes `build-provenance.json`, which carries `sourceDigest`, a SHA-256 over every shipped input, plus the compiler version, toolchain and lockfile digests.
- **Publishing:** it publishes atomically into `dist/libs/builder/generator`, and a failed build leaves the previous output untouched.
- **Staying in sync:** `generator-build-spec.mjs` is the single definition of the inputs. Keep it in sync when adding entry points, copied files or source trees.
- **Consumers read `dist`:** acceptance harnesses and the local Vite server read `dist`, not source. The rebuild and concurrency rules are in [agent-safety.md](agent-safety.md) ("The shared `dist` is live").

Testing details: [builder-testing.md](builder-testing.md). Hosts and the legacy engine: [builder-legacy-and-hosts.md](builder-legacy-and-hosts.md).
