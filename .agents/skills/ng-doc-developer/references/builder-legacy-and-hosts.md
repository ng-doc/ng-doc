# Builder hosts, the legacy engine and shared pieces

`@ng-doc/builder` currently ships two documentation engines side by side. Users pick one by choosing a builder or plugin; there is no runtime switch.

## Entry points

| Entry                                                    | Engine    | Source                                        | Used by                                                                                            |
| -------------------------------------------------------- | --------- | --------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `@ng-doc/builder:application`                            | legacy    | `libs/builder/application/`                   | `ng-doc:build-legacy`                                                                              |
| `@ng-doc/builder:dev-server`                             | legacy    | `libs/builder/dev-server/`                    | `ng-doc:serve-legacy`, `serve-legacy:poc`                                                          |
| `@ng-doc/builder:modern-application`                     | generator | `libs/builder/generator/angular/application/` | `ng-doc:build-modern`                                                                              |
| `@ng-doc/builder:modern-dev-server`                      | generator | `libs/builder/generator/angular/dev-server/`  | `ng-doc:serve-modern`                                                                              |
| Vite plugin (`generator/vite`, `generator/vite/angular`) | generator | `libs/builder/generator/vite/`                | `tools/scripts/serve-docs-vite.mjs`, `apps/ng-doc/vite.config.mjs`, Vite/Analog consumers          |
| `@ng-doc/builder:vite-application`                       | generator | `libs/builder/generator/vite/builders.ts`     | `ng-doc:build` (Vite build, server build, prerender)                                               |
| `@ng-doc/builder:vite-dev-server`                        | generator | `libs/builder/generator/vite/builders.ts`     | `ng-doc:serve`                                                                                     |
| `ng-doc` CLI (`generator/bootstrap/bin.js`)              | generator | `libs/builder/generator/bootstrap/`           | Standalone `generate` / `watch` / `dev`, and `prerender` (the Vite production pipeline)            |
| Schematics / `ng update`                                 | -         | `libs/builder/schematics/`                    | `ng g @ng-doc/builder:page`, `migrate-to-vite`, `vite-setup` (hidden, run by `ng add`), migrations |

- **Registry:** builders are registered in `libs/builder/builders.json`.
- **Schemas:** all builder `schema.json` files are _extensions_ merged over the installed `@angular/build` schemas: the legacy ones by `build-schema.js`, the generator ones by `build-generator.mjs`.
- **Progress:** the generator hosts (CLI, Vite plugin, modern builders) report generation progress through `progress/` (settings `NGDOC_PROGRESS`, `--progress`, the Vite plugin option `progress`, `ngDoc.progress`); see "Progress" in [builder-generator.md](builder-generator.md). The legacy engine keeps its own spinner (`helpers/print.ts`) unchanged.

The Vite engine for Angular CLI projects: the application is described in a Vite configuration with `createNgDocApplicationPlugin` (`vite/application.ts`: the `angular.json` build options `browser`, `server`, `polyfills`, `styles` and `assets`, a generated browser entry, `<base href>` from Vite's `base`, the server entry for prerendering) next to `createNgDocVitePlugin`. `buildNgDocViteApplication` (`vite/production.ts`) is the production pipeline behind the `vite-application` builder and `ng-doc prerender`: the browser build into `<outputPath>/browser`, the server build into `server/server.mjs`, then `prerenderNgDoc` (`vite/prerender.ts`), which renders every concrete route of the application's `Router.config` (`vite/route-inventory.ts`) in a child process (`vite/prerender-entry.ts`), keeps the shell as `index.csr.html` and writes `prerendered-routes.json`. Other `angular.json` build options passed to the plugin fail with `NGDOC_VITE_APPLICATION_OPTION`, which names their Vite or Analog equivalent (options without an effect under Vite only warn); keep that table in `vite/application.ts` complete, since the migration schematic generates these configurations (its spec reads the table and fails on an option the schematic doesn't know). The server entry keeps only `zone.js/node` and `@angular/localize/init` of the polyfills, as Angular does. The pipeline removes `server/` and `prerendered-routes.json` when it builds no server bundle, and never prerenders without one. The repository's own configuration is `apps/ng-doc/vite.config.mjs` (factory `ngDocSiteConfig`, which the `production-c` acceptance builds).

The migration to the Vite engine is the opt-in schematic `ng g @ng-doc/builder:migrate-to-vite` (`schematics/migrate-to-vite/`); `ng update` never runs it and keeps projects on the legacy builders.

- **What it does:** it reads the legacy `build`/`serve` targets of an `angular.json` or Nx `project.json` project (`@ng-doc/builder:application`/`dev-server`, or the `modern-*` builders), keeps them as `build-legacy`/`serve-legacy`, and writes `vite-application`/`vite-dev-server` targets whose configurations select the Vite mode of the same name. It generates `vite.config.mjs` (per-mode settings such as `fileReplacements`, `tsConfig` and `sourceMap` in a `modes` table; a build target without `defaultConfiguration` runs its plain options as the mode `default`; `ssr`/`prerender`/`routes` flags that differ per configuration go to the target's configurations; Nx `{workspaceRoot}`/`{projectRoot}`/`{projectName}` tokens are resolved in the Vite configuration and kept in the targets), wraps the `main.server.ts` default export with `withNgDocContentReady`, adds the Vite engine's tested tuple (`ng-doc.viteEngine` in `libs/builder/package.json`) to `devDependencies`, adds `/.cache/ng-doc` to `.gitignore`, repoints `extract-i18n`/`unit-test` build targets at `build-legacy`, and deletes the legacy generated folder once.
- **Analysis:** `analyze.ts` classifies every build and serve option as migrated, dropped, manual or blocking. Blocking findings (another builder, `localize`, an index not named `index.html`, no root component, an existing `vite.config.mjs`, a server entry whose default export is an NgModule (`NGDOC_MIGRATE_SERVER_NGMODULE`, `setup/source.ts` `serverEntryNgModule`): the Vite prerender calls `renderApplication` with a bootstrap function) change nothing.
- **Workspace files:** `setup/json-file.ts` (`JsonFile`) reads `angular.json`, `project.json`, `package.json` and tsconfig files as JSONC (comments and trailing commas, as the Angular CLI accepts them) and writes with `jsonc-parser` text edits in the file's own indentation and line endings, so the rest of the file keeps its layout. `jsonc-parser` is a direct dependency of `@ng-doc/builder` for this; don't go back to ng-morph's strict `JSONFile` here. Keep `KNOWN_BUILD_OPTIONS` and the classification in step with Angular's `application` builder and with `vite/application.ts`.
- **State:** `.ng-doc-migration/<project>/` holds `report.md`, `state.json` (created and changed files with layout-insensitive hashes, because the Angular CLI reformats what a schematic writes with Prettier; retargets; added dependencies) and `backup/`. Backups end in `.bak`, so no compiler or linter picks them up. A second run re-plans from the state and must leave the tree byte-identical; without the state, a `<name>-legacy` target next to a Vite target (or next to a target whose `configFile` exists) means "already migrated" and nothing changes. `--revert` first checks that every `-legacy` target still exists (else `NGDOC_MIGRATE_REVERT_TARGET`, nothing written), reports Vite targets edited since the migration (hashes in `targetHashes`), restores targets and backups, deletes the new engine's output and cache, and keeps files edited after the migration. A corrupted state fails with `NGDOC_MIGRATE_STATE`.
- **Reuse:** `setup/` (Vite configuration rendering, targets, dependencies, workspace reading and writing, root-component lookup, server-entry wrapping) takes no legacy input. The hidden `vite-setup` schematic (`schematics/vite-setup/`), which `ng add` runs for a new standalone project, reads Angular's own `build` target with `analyzeProject` (`keptBuildName: 'build-angular'`: the original target is kept under that name, and the outputMode finding doesn't offer it as a server) and applies the plan with `setup/`, without migration state or `--revert`. It accepts `@angular/build:application` and `@angular-devkit/build-angular:application`, blocks as `migrate-to-vite` does (plus an existing `build-angular`), never retargets the `serve` target it replaces (an explicit `options.buildTarget` would otherwise turn it back into an Angular target), and returns without changes when `build` already runs `vite-application`. A change to the analysis or to `setup/` affects both schematics: run both spec folders.
- **Tests:** specs in `schematics/migrate-to-vite/testing/` (`npx nx test builder -- migrate-to-vite`), with fixtures for a standalone SSR application, an NgModule application, custom options and an Nx workspace; `schematics/vite-setup/testing/` covers the Nx layout of `vite-setup`, and `libs/add` covers it on generated Angular applications.

The development modes:

- **Vite/Analog dev host with physical files** is the default and recommended development mode.
- **Angular CLI dev host with the new generator** (`modern-*` builders) is a thin fallback for Angular CLI users until they move to the Vite host: it generates, then runs Angular's own `application`/`dev-server` builder in-process on the written files. Its workspace watch ignores `node_modules`, `.git`, `.angular`, `.nx`, the generated, cache and output folders, and `session/watch-input-filter.ts` (`WatchInputFilter`) admits only recorded inputs: the union of the observations, glob matching, symlink aliases, and changes retained during a generation and replayed once its result records them. Generator failures are yielded as failed builder outputs between Angular's, and again after each native success while current; a watcher error ends the run. Architect runs a builder's teardowns only when it is stopped before the run completes, so the runner captures the teardowns Angular registers (a context proxy) and runs them from its own disposal, each bounded (10 s) so the watch and the session are always disposed; a stop during startup starts nothing further. The native smoke runs the real builders under a real Architect in a child process that must exit by itself after a stop or a fatal watcher error.
- The former virtual content mode (`developmentContent: 'virtual'`) was removed. See [builder-generator.md](builder-generator.md) ("Development content").

## The legacy engine (`libs/builder/engine`)

The legacy engine is RxJS-based:

- `build-ng-doc.ts` wires the pipeline.
- `engine/builders/` contains the page, API list and global builders.
- `engine/core/` holds the stores, triggers, watcher and operators.
- `engine/cache/` holds the file/property cache.
- `engine/nunjucks/` holds the templating.

It runs inside the Angular CLI builders and writes its output to the configured `outDir` (for this repo, `ng-doc/`). The app imports that output as `@ng-doc/generated`.

- **Status:** the legacy `application`/`dev-server` builders are deprecated in 22.0 (`apps/ng-doc/docs/upgrade/legacy-builders`). They still ship and work, and they stay the default for existing projects: `ng update` keeps them, and moving to the Vite engine is the opt-in `migrate-to-vite`.
- **Fixing it:** fix bugs in it when asked, but put new features in the generator unless the task says both engines need them.
- **Parity:** the generator is expected to produce equivalent product behaviour (routes, pages, search, keywords, demos, playgrounds, SSR/prerender). A behaviour change in one engine that users can observe should be mirrored or explicitly documented.
- **Removal:** don't delete legacy code or builders without an explicit migration and rollback plan.

### Deliberate difference: `onlyForTags`

The new engine applies `onlyForTags` of pages and categories; the legacy engine ignores it (its check was removed in the v18 rewrite). This difference is intended.

- **Build tags** name the build configuration:
  - `modern-*` builders: the configuration name(s), or the target's `defaultConfiguration` when the CLI passes none; override with `ngDoc.tags`.
  - Vite plugin: the Vite mode; override with `generator.discovery.tags`.
  - `ng-doc` CLI: `production` for `generate`, `development` for `dev`/`watch`; override with `--tags`.
- **Filtered entries don't exist in the build.** A filtered entry, and everything in a filtered category, has no route, navigation item, search record, keyword or output. `DiscoverySnapshot.filtered` only names them for diagnostics: a link to a filtered guide's keyword fails with `CONTENT_KEYWORD_FILTERED`.
- **Digest:** only the tags that some `onlyForTags` names enter the configuration digest, so a change of selection is a FULL generation and projects without `onlyForTags` keep their cache across serve and build.
- **Acceptance baselines** recorded with the legacy engine still contain such entries, for example the site's Develop sandbox (`onlyForTags: ['development']`). Gates that compare against them derive the expected removals with `acceptance/only-for-tags/removals.mjs` (discovery with and without the build's tags) and require them; any other missing route still fails.

### Deliberate difference: the default syntax theme

Without `shiki.themes`, the new engine highlights code with NgDoc's `css-variables` theme (`ngDocSyntaxTheme()` in `libs/core/constants/syntax-theme.ts`): token colours are `var(--ng-doc-syntax-*)`, so code follows the site theme. The legacy engine keeps `github-light`/`ayu-dark` (the `processHtml` defaults in `libs/utils`, and the runtime highlighter's fallback for an empty theme name), so its output is unchanged. Both engines, the Vite plugin (no `themeModules` entry needed) and `@ng-doc/app`'s highlighter resolve the name `css-variables` to that theme. Shiki mutates a theme object it loads, so always pass a new `ngDocSyntaxTheme()`.

### Deliberate difference: the symbol view of API pages

The new engine renders every API page with `templates/symbol/{header,page,details,decorators,extended-by,see-also,members}.html.nunj` (`semantic/fragments.ts`); the legacy engine keeps `api-header.html.nunj` and `api-page-content.html.nunj`, so its output is unchanged. The symbol view puts the details after the description as a definition list, adds a hidden rail copy of them (`[data-ng-doc-rail-details]`, with the kind and scope) that `NgDocPageComponent` moves into the TOC rail (`NgDocPageToc.details`), a declaration panel (`apiDeclaration` for classes, interfaces and enums; the legacy presentation for functions, type aliases and variables), an "Extended by" list of derived classes (out of See Also), and, for classes, interfaces, type aliases and enums, one members table inside `<ng-doc-members>`, which `@ng-doc/app`'s `membersProcessor` turns into `NgDocMembersComponent` (it hosts `NgDocMembersFilterDirective`: tabs when there is more than one group, name filter, expandable method rows). Functions keep their Returns, Parameters and Overloads sections. Every anchor of the per-section layout is kept, so keywords and links are identical: group rows hold the old section headings (`<h3>`), property, accessor and enum rows the same `dataSlug` attributes, method and call-signature rows `dataSlugType="method"` (slugged like the old `<h3>`), the declaration panel of functions, type aliases and variables the `presentation` heading anchor, and the Extended by list the `see-also` anchor when the page has no `@see` tags. `semantic/testing/rendering.vitest.ts` compares the anchors of both layouts for every declaration kind. Decorator chips carry `data-ng-doc-decorator` (signal inputs, models and outputs count as `Input`/`Output`), which `parts/decorators.scss` maps to the `--ng-doc-*-decorator-background` hues. The members table's search records belong to other sections than the legacy ones, so `parity.mjs` compares API pages by text (`KNOWN.search.symbolView`).

### Deliberate difference: API summaries and API list locations

Only the new engine writes these, so the runtime treats them as optional and the legacy output is unchanged:

- **Summaries.** `semantic/api-summary.ts` reads each declaration's header and the first paragraph of its doc comment syntactically (no checker) into `DeclarationDescriptor.signature`/`description`. The records of an API page that belong to no section carry `kind`, `signature` and `description` (`compiler/assemble.ts`), and `api-list.json` items a `description`. The search palette previews them and the API index shows the description column. `acceptance/production/parity.mjs` leaves these fields (`KNOWN.search.fields`) out of the legacy comparison.
- **List locations.** An API entry's route carries `data: { ngDocApiListSegment }` (`routes.ts.nunj`) and the generated context lists every segment (`NgDocContext.apiLists`), so the palette requests exactly those lists (none on a site without an API). Both template blocks render only when the value is defined.

## Shared code: changes affect both engines

| Path                                       | Shared how                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `libs/builder/templates/**`                | Nunjucks templates for generated TS/HTML. Both engines use them, and the generator copies them into its bundle.                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `libs/builder/helpers`, `parsers`, `types` | Bundled into the generator; imported by the legacy engine. Every order that reaches output (untitled-order navigation entries, API members, keywords, discovery entries, the output manifest, diagnostics) uses the one fixed English collator, `compareText` (`helpers/text-order.ts`; `compareNavigationTitles` delegates to it), never `localeCompare` or the process locale. `compiler/locale.vitest.ts` compiles one tree in a Swedish and a C process and requires the same bytes, and fails on a `.localeCompare(` in the shipped builder sources. |
| `libs/core`, `libs/utils`                  | Types, HTML post-processing and highlighting, used by both engines and the runtime.                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `libs/app` + `libs/ui-kit`                 | The runtime that renders generated content, whichever engine produced it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

When you change shared code:

- run the builder's specs (`npx nx test builder`) **and** the generator runner groups that exercise it (usually `content`, `semantic`, `outputs` and `compiler`);
- remember that changing any of the generator's hashed inputs changes its `sourceDigest`. The rebuild rules are in [agent-safety.md](agent-safety.md) ("The shared `dist` is live").

## Package shape

- **Module formats:** `@ng-doc/builder` is CommonJS (`"type": "commonjs"`), compiled with `tsc` into `dist/libs/builder`. The generator is an esbuild ESM bundle under `dist/libs/builder/generator`, with its own `package.json` (`"type": "module"`).
- **Dependencies:** every runtime import of the generator must be declared in `libs/builder/package.json` (`dependencies` or `peerDependencies`). The build fails on an undeclared one. The same holds for the runtime `require`s retained in the vendored Analog plugin (`RUNTIME_REQUIRES` in `tools/scripts/build-analog-compatibility.mjs`), except one behind an upstream branch for an older Angular major (`maxAngularMajor`), which never runs on the Angular major the package pins `@angular/compiler-cli` to.
- **Angular builders:** the builder depends on `@angular/build`, not `@angular-devkit/build-angular`. The legacy builders call its public API (`buildApplication`, `executeDevServerBuilder`) and print their own progress spinner (`helpers/print.ts`).
- **Optional hosts:** Analog, Vite and Angular CLI integrations must stay optional. The core generator must install and run without the Analog plugin.
- **Optional peers are ranges; the tested tuple is exact.** The optional peers (`vite`, `@analogjs/vite-plugin-angular`, `@angular/compiler`, `@angular/compiler-cli`) only keep npm from refusing an install: an exact optional peer fails with `ERESOLVE` whenever another package (Vitest, Angular's own tooling) brings in a different version, even for legacy-engine users. The exact versions the Vite engine is tested with live in `ng-doc.viteEngine`, which `ng add` and `migrate-to-vite` install. The engine enforces Vite at start-up (`vite/vite-version.ts`, `NGDOC_VITE_VERSION`: plugin creation, its `config` hook and the production pipeline); `SUPPORTED_VITE_VERSION` must equal `ng-doc.viteEngine.vite` (a test compares them). Analog is vendored into the bundle, so the installed one only supplies types.
- **Analog compatibility:** Analog-specific compatibility is pinned to the Analog version in the root `package.json`, through `tools/compatibility/` and `tools/scripts/build-analog-compatibility.mjs`. Upgrading Analog means updating that policy too.
