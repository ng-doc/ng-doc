# Libraries: `app`, `ui-kit`, `core`, `utils`, `keywords-loaders`, `add`

## What each library is

| Library                 | Package                    | Build                              | Public API                                                                                                                                                                                                                                                                                      |
| ----------------------- | -------------------------- | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `libs/app`              | `@ng-doc/app`              | ng-packagr (`@nx/angular:package`) | `libs/app/index.ts` + secondary entry points (`@ng-doc/app/components`, `/services`, `/tokens`, `/providers`, `/processors`, `/type-controls`, ...).                                                                                                                                            |
| `libs/ui-kit`           | `@ng-doc/ui-kit`           | ng-packagr                         | `libs/ui-kit/index.ts` + secondary entry points (`@ng-doc/ui-kit/components`, `/cdk`, `/directives`, ...); ships `assets/`.                                                                                                                                                                     |
| `libs/core`             | `@ng-doc/core`             | `tsc` (CommonJS)                   | `libs/core/index.ts`; deep imports via `@ng-doc/core/*`. Framework-agnostic at runtime: Angular appears only in type positions (for example `Type`, `Route` in the page/category interfaces); never import Angular values. It is used by the builder in Node and by the runtime in the browser. |
| `libs/utils`            | `@ng-doc/utils`            | rollup (ESM)                       | `libs/utils/index.ts`: HTML processing used by the builder (Node only).                                                                                                                                                                                                                         |
| `libs/keywords-loaders` | `@ng-doc/keywords-loaders` | rollup                             | `libs/keywords-loaders/index.ts`: `ngKeywordsLoader`, `rxjsKeywordsLoader`, NgDoc loader.                                                                                                                                                                                                       |

Peer dependencies of `app` and `ui-kit` pin Angular to the current major (`>=22 <23`). Keep them aligned with the root `package.json` when upgrading Angular.

## Public API and entry points

- **Leaf folders:** every folder in `app`/`ui-kit` is its own ng-packagr entry point. For example, `libs/ui-kit/components/button/` contains `button.component.ts`, `.scss`/`.html`, an `index.ts` barrel and an `ng-package.json` with `{ "lib": { "entryFile": "index.ts" } }`.
- **Parent barrels** re-export children by their **package path**, for example `export * from '@ng-doc/ui-kit/components/button';` in `libs/ui-kit/components/index.ts`.
- **Adding a folder:** add both `index.ts` and `ng-package.json`, and add the export to the parent barrel.
- **Imports across entry points** (including inside the same library) use the `@ng-doc/<lib>/<path>` alias, never a relative path out of the entry point. ng-packagr fails otherwise.
- **The public API is the barrels.** Anything a barrel exports is public. Separately, the site's API reference (`apps/ng-doc/docs/ng-doc.api.ts`) documents every exported declaration in the files its scope globs include. So:
  - export deliberately;
  - document exported symbols with JSDoc;
  - treat renames and removals as breaking changes (a `BREAKING CHANGE:` footer with a migration note, and a schematic migration in `libs/builder/schematics` when it is mechanical; see [code-style.md](code-style.md)).
- **Shared shapes:** types shared between the builder and the runtime (page/category/API configuration, generated content modules) live in `libs/core`. That lets the runtime and the generator agree without app-to-builder imports.

## Angular style in these libraries

Current conventions, followed consistently:

- **Components:** standalone only (no NgModules); `standalone: true` is redundant on Angular 22, so don't add it.
- **Change detection:** `ChangeDetectionStrategy.OnPush` on every component (lint error otherwise).
- **Dependency injection:** `inject()` rather than constructor parameters.
- **Templates:** built-in control flow (`@if`, `@for`, `@switch`); no `*ngIf`/`*ngFor`.
- **Subscriptions:** `takeUntilDestroyed()` for subscription cleanup.
- **Selectors:**
  - Components use `ng-doc-` (`ng-doc-sidebar-item`), often as attribute selectors on native elements (`button[ng-doc-button]`).
  - Directives use camelCase attribute selectors with the `ngDoc` prefix (enforced).
- **Class names:** `NgDoc<Name>Component|Directive|Pipe|Service`.
- **Styles:** SCSS files next to the component, using `:host`, the shared mixins in `libs/<lib>/styles` and `--ng-doc-*` CSS custom properties. Load Sass files with the module system (`@use`, with the namespace, and `sass:map` and the other built-in modules); Sass `@import` and global built-ins such as `map-get` are deprecated, and the serve and build output must stay free of their warnings. Plain CSS imports (`@import '...css'`) are fine. The packages ship compiled CSS (`@ng-doc/app/styles/*.css`, `@ng-doc/ui-kit/styles/main.css`), not SCSS. Variants are expressed as `data-ng-doc-*` attributes, not BEM classes. Theme values come from custom properties; don't hard-code colours.
- **SSR safety:** the runtime is server-rendered and prerendered. Guard browser-only APIs (`window`, `document`, `Element.animate`, `matchMedia`, ...) with platform checks or `afterNextRender`, and use injected tokens (`DOCUMENT`, `@ng-doc/app` tokens) instead of globals.
- **Server DOM:** the server renders with domino, which implements less than a browser. For example, its `innerHTML` setter works only on HTML elements, and since Angular 22.2 a component created through a `ViewContainerRef` can be an SVG element (it takes the namespace of the container's parent). Parse markup with an HTML `<template>` instead (see `components/icon`). `libs/ui-kit/testing/icon/icon-server.spec.ts` shows how a spec renders with the real server platform.

### Signals

The libraries use signal APIs: `input()`/`input.required()`/`model()`/`output()`, `computed()`, signal queries (`viewChild()`, `contentChild()`, ...), `host: {}` metadata instead of `@HostBinding`/`@HostListener`, and `@Service()` instead of `@Injectable({ providedIn: 'root' })`.

- **Enforced:** the rules in `tools/eslint/angular-modernization.mjs` (`prefer-signals`, `prefer-signal-model`, `prefer-output-emitter-ref`, `prefer-host-metadata-property`, `prefer-service-decorator`, `no-uncalled-signals`, `template/prefer-control-flow`) are errors in both libraries. Specs and `testing/` are exempt.
- **Known exceptions:**
  - `compareFn` and `displayValueFn` of `ng-doc-combobox-host` stay decorator inputs because `di-controls` host interfaces call them as functions (inline `eslint-disable` with the reason). The `di-controls` base classes also keep their own decorator inputs (`value`, `disabled`).
  - `ngDocChecked` of `NgDocCheckedChangeDirective` (`libs/ui-kit/directives/checked-change/checked-change.directive.ts`) is an `input()` plus a separate `output<boolean>()`, not a `model()`, so `(ngDocCheckedChange)` keeps a `boolean` `$event` while the input also accepts `null` (indeterminate); it carries an inline `prefer-signal-model` disable.
  - `@Service()` is for root services built with `inject()`. Classes provided per component (`NgDocContentController`, `NgDocContentAnchorController`), class interceptors (`NgDocCacheInterceptor`) and search engines created by a factory with constructor arguments (`NgDocDefaultSearchEngine`) keep `@Injectable()` or no decorator.
- **The playground contract.** The playground classes the builder generates (`libs/builder/templates/playgrounds.ts.nunj`) extend `NgDocBasePlayground`: they declare `target`, `playground = viewChild(target)`, `viewContainerRef = viewChild(target, { read: ViewContainerRef })` and `configData`, and their templates read the signal inputs (`properties()['name']`, `@if (content()['slot'])`, built by `getPlaygroundTemplateInputs` and `buildPlaygroundDemoTemplate`). The base class detaches its view until `ngOnInit` has read the target's defaults (signal inputs are called). Both engines render that template, so the builder and `@ng-doc/app` change it together. The generated classes still import `CommonModule`, because user playground templates may use its directives and pipes (for example `| json`).
- **Public inputs are public API.** Converting `@Input() foo` to `foo = input()` changes how consumers read it (`foo()`) and whether they can set it imperatively. Treat such conversions of exported components as potentially breaking, and call them out.
- **Forms:** Signal Forms (`form()` and `[formField]` from `@angular/forms/signals`) hold the filter and query models of the search palette (`components/command-palette`) and the API index (`components/api-list`). Elsewhere, don't introduce them without an explicit decision. The ui-kit form controls are `ControlValueAccessor`s built on `di-controls`, and `libs/ui-kit/testing/forms` checks that they work with `ngModel`, reactive forms and Signal Forms' `[formField]`. Keep that spec passing when you change a control.
- **Zone.js:** the site is zoneless (`provideZonelessChangeDetection()`, no `zone.js` polyfill), like applications created with Angular 21 or later, but users' applications may still run with Zone.js. Code must work with and without Zone-triggered change detection; the specs run both ways (see Tests). Don't wait for `NgZone.onStable` (it never emits zoneless); schedule with signals, `afterNextRender`/`afterRenderEffect` or `markForCheck`, and use `NgZone.runOutsideAngular` only to keep frequent listeners from triggering change detection in zone apps.
- **Legacy constructors:** the `constructor(...args: unknown[])` overloads left by the automated `inject()` migration have been removed. Don't add them back; classes use `inject()` and a parameterless constructor.
- **Page navigation:** the generated page routes (`page.ts.nunj`, `page-wrapper.ts.nunj`) wrap the route of a page with a content source in `ɵwithNgDocContent(route, source)` (`helpers/content-preload.ts`). Its resolver loads the content of every route of the navigation at once, before the router activates them, and `NgDocContentController` applies a preloaded payload synchronously, so the previous page stays until the next one renders with its content. The wait is bounded (`ɵNG_DOC_CONTENT_WAIT`, 8 s); after it the page opens and waits for the same pending load, and the resolver clears its timer so a server render never waits it out. Both halves are needed: `testing/content-boundary/navigation-swap.spec.ts` fails without either. The router copies route objects when it loads them but keeps their `resolve` maps, so a route's source is found through its resolver function (`ɵngDocRouteContentSources`).
- **Preloading:** `NgDocPreloadingStrategy` and `NgDocRoutePreloader` (`services/route-preloader`) preload a page's route chunks and content when the reader points at, focuses or touches a link to it (one capture listener on the document), and the previous and next guides at idle, only under `NG_DOC_ROUTE_PREFIX` and never through a `canMatch` route. The site enables it with `withPreloading(NgDocPreloadingStrategy)`. Never preload every route (`PreloadAllModules`): the site has hundreds of pages. The path matching reads the router's internal `_loadedRoutes`, as Angular's own preloader does.

## Tests

- **Test setup:** `app` and `ui-kit` run their specs with Vitest through `@angular/build:unit-test` in jsdom, each spec file isolated. The builder compiles the specs ahead of time with the full type checker, so a type error in a spec fails the run. `test` loads zone.js and `test-zoneless` does not (the `build-specs` target and its `zoneless` configuration); `vitest.config.ts` and `vitest.zoneless.config.ts` set the environment and coverage directory, and `test-setup.ts` swaps in jsdom's `AbortController`. Specs are `*.spec.ts` next to the source or under `testing/`.
- **Running them:** `npx nx test app` or `npx nx test ui-kit`, and `npx nx run app:test-zoneless` / `ui-kit:test-zoneless` for the zoneless run.
- **Zoneless smoke host:** `libs/app/testing/zoneless/zoneless-smoke.spec.ts` renders a docs route the way a generated site does (root, header with search, sidebar, page wrapper, a page with a code block, a demo and a playground) and the search palette, in a zoneless application, without calling `detectChanges()`. Extend it when a new runtime feature needs change detection to reach the page.
- **Search index:** the specs under `libs/app/testing/search-index` have their own Vitest config with a coverage gate, and `test`/`test-zoneless` exclude that folder. Run them with `npx nx run app:test-search-index`.
- **Both change-detection modes:** wrap component specs in `describeChangeDetection` and pass its `providers` to `TestBed`. `libs/app` exports it from `testing/change-detection/change-detection-modes.ts`. `libs/ui-kit` specs declare it locally (see `libs/ui-kit/testing/change-detection/change-detection-modes.spec.ts`), because the site's API reference documents every exported declaration under `libs/ui-kit`, tests included, and an exported test helper would become an API page.
- **Library sources:** the unit-test builder resolves `@ng-doc/*` imports through the `tsconfig.base.json` paths, so specs load the library sources, not `dist`, and need no build first.
- **Node specs:** specs that need Node rather than a DOM (the stylesheet contracts in `testing/styles`, `testing/types`) start with a `@vitest-environment node` docblock. Specs are bundled before they run, so they find workspace files from the working directory (`workspaceRoot()` in `testing/styles/css-surface.ts`), not `__dirname`.
- **Zones in specs:** zone.js has no Vitest patch, so under `@angular/build:unit-test` the specs run in the root zone, not in a `ProxyZone`. No spec uses `fakeAsync` or `waitForAsync` today; a spec that needs them must set up a `ProxyZone` itself (or use real timers, `vi.useFakeTimers()` and `fixture.whenStable()`).
- **Module mocks:** `vi.mock` works for packages (`shiki`, `esthetic`) but not for relative paths; replace workspace dependencies through TestBed providers.
- **CSS variables:** `libs/app/testing/styles/css-variable-contract.spec.ts` checks every `--ng-doc-*` name against `public-variables.json`, records where each variable is read (`variable-readers.json`), where a component sets one locally (`variable-declarations.json`) and what it resolves to in every theme (`variable-values.json`), and `css-contrast.spec.ts` holds the default theme to WCAG AA. A change that adds, retires, moves, stops reading, sets locally or revalues a variable updates those files: run `NGDOC_UPDATE_CSS_CONTRACT=1 npx nx test app --skip-nx-cache` (refused when `CI` is set) and review the JSON diff.
- **Coverage:** it is thin in these libraries. Add a spec when you change behaviour, especially for pipes, services and helpers.
- **Rendering:** the generated-content rendering path is exercised end to end by the docs site. See [docs-app.md](docs-app.md).

## `libs/add` (`ng add`)

`@ng-doc/add` holds the `ng add` schematics (`libs/add/schematics/collection.json`, `ng-add/`). It is built with `tsc` and has Vitest specs (`npx nx test add`, which type-checks them with `tsc` first). When installation steps change (new providers, config files, assets), update the schematic and the installation guide in `apps/ng-doc/docs/get-started/installation` together. Builder schematics (page, category, API, migrations) live in `libs/builder/schematics` instead.

Rules for the `ng add` output:

- **No duplicates.** Array entries are matched by function name (`utils/add-array-entry.ts`). An existing `provideRouter`, `RouterModule.forRoot` (also inside an imported routing module) or `provideHttpClient` call is extended with the missing routes, features or options instead of being added twice. Duplicate calls left by earlier versions are merged (without `withFetch()`). Inline routes get the NgDoc routes before a trailing `**` route. A second run changes no file (`testing/ng-add-idempotent.spec.ts`).
- **All or nothing per step.** A step that edits TypeScript creates its own ng-morph project, adds imports before it edits arrays, saves only on success and resets the active project in `finally`, so a failed step never reaches the tree through a later save. When code cannot be edited safely (a variable instead of an array or options literal), log what to add by hand; never fall back to a second `forRoot` (`testing/ng-add-edge-cases.spec.ts`).
- **Zone-agnostic.** Add no change-detection provider and no `zone.js` polyfill; the application keeps its mode (`testing/ng-add-zoneless-app.spec.ts` covers zoneless and zone.js apps). Don't add deprecated Angular features such as `withFetch()`.
- **Both app kinds.** Standalone (`bootstrapApplication`) and NgModule (`platformBrowser().bootstrapModule`, or the older `platformBrowserDynamic`) applications are supported, with Angular 22 `ng new` file names (`app.ts`, `app-module.ts`).
- **Engine choice** (`utils/select-engine.ts`, option `--engine vite|legacy`). A new standalone application on Angular's `application` builder gets the Vite engine. Without `--engine`, an NgModule application and an application on another builder (`@nx/angular:application`, `browser`, a custom one) get the legacy builders with an info line; `--engine vite` throws for them (`NGDOC_ADD_ENGINE`, or the Vite setup's `NGDOC_VITE_SETUP_BLOCKED`). A project where any target runs an `@ng-doc/builder:*` builder keeps its builders: `ng add` never switches engines (it logs `ng g @ng-doc/builder:migrate-to-vite` for legacy projects). `replace-builders.ts` runs only when `build` or `serve` already uses an NgDoc builder (or for a new project), and leaves NgDoc builders alone (a `modern-*` target stays `modern-*`).
- **Vite setup is the builder's.** The common steps (styles, assets, providers, layout, tsconfig, `.gitignore`) run on the Angular `build` target first; then `externalSchematic('@ng-doc/builder', 'vite-setup')` (`libs/builder/schematics/vite-setup/`, a hidden schematic) reads that target with `migrate-to-vite`'s `analyzeProject` and `setup/`, writes `vite.config.mjs` and the Vite targets, keeps the Angular options as `build-angular` (retargeting `unit-test`/`extract-i18n`), wraps `main.server.ts`, adds `/.cache/ng-doc` and the Vite dependencies. Blocking findings throw `NGDOC_VITE_SETUP_BLOCKED` before anything is written. Don't copy that code into `libs/add`.
- **Task order.** `ng-add-setup-project` runs as a task _before_ `ngAdd`'s install task (that install prunes `@ng-doc/add` itself). `@ng-doc/add` therefore depends on `@ng-doc/builder` (`libs/add/package.json`, rewritten to the release version by `plugins/semantic-release/update-dependencies.js`), so `vite-setup` is resolvable during setup; it runs with `skipInstall`, and the following install also installs Vite.
- **Legacy budgets.** For a project new to NgDoc, the legacy setup raises an `initial` budget `maximumError` of exactly 1 MB (the `ng new` default) to `5mb` (`steps/raise-initial-budget.ts`): the production build otherwise fails. Other values and existing NgDoc projects are left alone. The Vite engine has no budgets and keeps `build-angular` as it was.
- **Second run on a Vite project.** The Vite targets hold no Angular options: the styles, assets and `allowedCommonJsDependencies` steps are skipped, and the steps that read the browser entry or `tsConfig` read `build-angular`, or `build-legacy` after `migrate-to-vite` (`utils/get-build-options-target.ts`). The run changes no file.
- **Specs.** `testing/ng-add-runner.ts` registers `@ng-doc/builder` from `libs/builder/schematics/collection.json`, so the specs run the builder's sources, never the build that `node_modules` links to. `testing/ng-add-vite-engine.spec.ts` generates real Angular 22 applications with `@schematics/angular` (SSR and CSR, zoneless and zone.js, standalone and NgModule). The legacy-shaped fixtures of the older specs pass `engine: 'legacy'`. `runSchematic` changes the tree it is given: snapshot a tree before a run you compare against.
